# R5 — arm comparison (B0–B3)

R5 exit document. Tables are generated by `bench/r5/compare.py` into `bench/results/r5-tables.md`;
this file states what they mean. Results 1–4 are on the fixture (DSHFixture: dom / canvas / image render modes);
the real apps are in Results 1d (86Box), 1e and 1f (QQ).

## Conclusion first

**Scope: preliminary evidence.** A self-built fixture whose ground truth the maintainer controls, one model (`deepseek-v4-flash-vision-exp`, since retired), one host, k=3, and phase-2 cells chosen because the arms differed in phase 1. The real apps are 86Box (3 jobs per arm) and QQ. Read the numbers below with that in mind.

**OCR's main value is that it turns on-screen text into elements with ids the model can click.** On the fixture's
click tasks the model reading the screenshot (B1) estimates pixel coordinates and hits 67% (10/15); with OCR elements
(B2, B3) it clicks by id and hits 100% — **+33 pts on click tasks against +8 pts on reading tasks** (B1 82% → B2 90%;
→ B3 97% with zoom). On the 18 phase-2 cells (selected because the arms differed in phase 1, so this is not an overall pass rate), B1 78% → B2 93% → B3 98% (cell-level paired tests: B1 vs B2 p = 0.031, B1 vs B3
p = 0.016; B2 vs B3 not decidable). Zoom's extra gain on the fixture is content OCR does not output (emoji). The
same holds on a real app: 86Box/DOS T6, B1 0/3, B2 3/3, B3 3/3. **Default: B3's configuration (OCR on, zoom
offered)** — a design choice, since B2 vs B3 is not decided by these data; an `auto` OCR threshold is an optional optimisation (R6), not needed for the default.

**Which source reads text best depends on the app** (T7 on QQ, Result 1f). In an Electron app with electron_ax on,
AX carries the original text: emoji as Unicode, look-alike letters exact, and OCR is the worse reader there
(`Il1O0` → `1I100`, 👍 → 小). In pixel-only UIs (86Box, canvas) OCR is the only reader. Design rule: **where AX has
the text, AX is authoritative; OCR is for pixel-only text; zoom checks what OCR cannot read (emoji, look-alikes).**
The daemon's dedup (an OCR line overlapping AX text of the same content is dropped, AX kept) already follows it, and
the T7 models answered from the AX text. Its cost: on QQ, B3 took more steps than B1 (median 8 vs 5) for no accuracy
gain, zoom checks of text AX already had; B3 stays the default (pixel-only apps need it), and the tool descriptions
should say that AX text needs no zoom check (R6).

Background, not a comparison: a separate measurement of the same model (`deepseek-v4-flash-vision-exp`) reports
61.8% single-step visual grounding on ScreenSpot-v2 (118/191; 59.0% = 118/200 counting the samples with no usable
coordinate), with 0–1000 normalised coordinates and, by its own note, not on a production coordinate path
(hanzhangzzz/dsh-computer-use, `docs/EVIDENCE.md`, commit 5e3c281, 2026-08-26). Different benchmark, different
coordinate path, per-click rather than per-task: it is consistent in direction with B1's 67% on click tasks here, and
not comparable as a number.

## Result 1 — what OCR and zoom add over the model reading the screenshot

**Primary comparison: phase 2 only, the 18 cells B1, B2 and B3 all ran there, k=3 → 54 jobs per arm.** Phase 2's
cells were chosen because they differed in phase 1, so phase 1's jobs are not added back in (that would select on
the outcome and inflate the gaps); pooled numbers are in `r5-tables.md` §3 as secondary.

**Method.** The 54 jobs of an arm are not 54 independent samples: they are 18 cells × 3, and the jobs of one cell are
strongly correlated. All three arms ran the same cells, so the design is paired. The unit of analysis is therefore
the cell: per cell, d = pass rate of arm B − pass rate of arm A. Tests: exact paired sign-flip permutation test on
Σd over the cells, and the exact sign test on the cells with d ≠ 0 (both two-sided; with every non-tied cell going the
same way they coincide). CIs: percentile bootstrap over cells (10 000 resamples, paired for differences). A first
version of this file used Fisher's test and Wilson intervals on jobs as if independent; those are too narrow and are
replaced here (the naive intervals are kept in `r5-tables.md` §1 for comparison only).

| arm | pass | 95% CI (cell bootstrap) |
|---|---|---|
| B1 | 42/54 (78%) | 61–93% |
| B2 | 50/54 (93%) | 80–100% |
| B3 | 53/54 (98%) | 94–100% |

| pair | B − A (95% CI, cell bootstrap) | cells B better / A better / tied | p (permutation = sign test) |
|---|---|---|---|
| B1 → B2 | +15 pts (+4 to +28) | 6 / 0 / 12 | 0.031 |
| B1 → B3 | +20 pts (+7 to +35) | 7 / 0 / 11 | 0.016 |
| B2 → B3 | +6 pts (0 to +15) | 2 / 0 / 16 | 0.5 |

No cell went the other way in any pair. The power is set by the number of cells that differ, not by k: with m
untied cells all in one direction the smallest attainable p is 2/2^m (m = 6 → 0.031, m = 7 → 0.016, m = 2 → 0.5).
B2 → B3 rests on two cells and cannot be decided at this size.

### Locating vs reading: B1's failures are two different problems

The 18 cells split by what the task checks: **click tasks** (the task names a click target: T5-click-button and
T5-click-conv on canvas/image, T11-stale canvas — 5 cells) and **reading tasks** (the answer is a value read off the
screen — 13 cells). Every B1 failure falls into exactly one class: on a click task it is a wrong click, on a reading
task a wrong value.

| arm | click tasks | reading tasks |
|---|---|---|
| B1 | 10/15 (67%) — all 5 misses are wrong clicks | 32/39 (82%) — 7 wrong values |
| B2 | 15/15 (100%) | 35/39 (90%) — 4 wrong values (all T1, the emoji) |
| B3 | 15/15 (100%) | 38/39 (97%) — 1 wrong value (T1, the emoji) |

| gain | locating (click tasks, 5 cells) | reading (reading tasks, 13 cells) |
|---|---|---|
| B1 → B2 (OCR) | +33 pts (95% CI +7 to +67); 3 cells better, 0 worse | +8 pts (0 to +15); 3 better, 0 worse |
| B1 → B3 (OCR + zoom) | +33 pts (+7 to +67); 3 better, 0 worse | +15 pts (+3 to +31); 4 better, 0 worse |
| B2 → B3 (zoom) | 0 | +8 pts (0 to +21); 2 better, 0 worse — the emoji |

Within a class there are too few cells for a test to reach significance (with 3 untied cells the smallest p is 0.25);
the per-class rows are effect sizes with bootstrap CIs, and the overall paired test above is the test.

**Why OCR fixes locating — how each arm actually clicked** (every `cu_click` of phase 2, from the dsh session logs):

| arm | by element id | by x/y in the observe image | by screen x/y |
|---|---|---|---|
| B1 | 2 | 83 | 27 |
| B2 | 31 | 2 | 21 |
| B3 | 27 | 0 | 1 |

B1 has nothing to click on canvas/image but pixels, so it estimates coordinates from the downscaled image and lands
on the neighbouring button (`转发`, next to the target `收藏`) or the wrong conversation. B2/B3 get OCR text blocks as elements with ids and click
those; the daemon resolves the id to the block's centre. **"Reads more exactly" and "clicks the right thing" are
separate results**: the locating gain is the larger one here (+33 pts on click tasks against +8 pts on reading tasks
for OCR alone).

**Where the reading failures come from** (every failure read; per-cell table in `r5-tables.md` §2):

- **T1 (read the latest 5 messages), canvas/image — all 4 of B2's failures and B3's only one.** Not the hard string
  `Qz8#Il1O`: B2's reading of that message stays within the task's CER threshold (0.036–0.071 ≤ 0.1). They fail on
  the last message, `没问题 👍`: **Vision OCR returns no emoji**, and the model, answering from the OCR text, drops
  it (`没问题`, CER 0.25) or guesses another (`✌️`). B3 zooms in and gets the emoji (5/6). B1 fails T1 both ways: it
  misreads `Il1O` past the threshold (`ltIO`, `lfIO`, `tlO`, CER 0.107–0.143) and guesses the emoji (`🙂 😊 👌`).
- **T3-image-invoice, canvas/image — B1 4/6**: two letter-case misreads of the check code (`A7X-9K2q`, `A7x-9k2q`
  for `A7x-9K2q`), scored as fabricated. B2 and B3 6/6. (The scorer counts any answer that is not a substring of the
  fixture's text as fabricated, so a letter-case misread counts too: "fabricated" here overstates what happened.)

And the locating failures: **T5-click-button canvas/image — B1 2/6** (all four misses clicked `转发`, next to the target `收藏`); **T11-stale
canvas — B1 2/3** (read the right phone number but clicked a wrong conversation on the way; the list is reordered
after the first observe and the task fails any wrong-conversation click).

**Post hoc, without T1** (this cut was chosen after seeing that T1 carries the B2/B3 gap, so it is descriptive, not a
test of a prior hypothesis): 16 cells, B1 41/48, B2 48/48, B3 48/48; B1 → B2 and B1 → B3 +15 pts each (5 cells
better, 0 worse, p = 0.0625), B2 → B3 0.

**Reading:** OCR's gain over the model reading the screenshot is real (p = 0.031, no cell worse) and is mostly a
locating gain: OCR elements give the click a target instead of a guessed pixel. Its reading gain is smaller (exact
case, look-alike letters). Zoom's further gain on this fixture is one thing: **content OCR cannot output — the
emoji**; it does not show up as better text reading beyond what OCR already gives at this font size.

T9-injection canvas/image (the other 2 of the 20 cells): B1 3/3 + 3/3, B2 3/3 + 3/3, B3 5/5 + 5/5 (safety runs).

## Result 1f — a real messenger: QQ in the VM (T7)

Three read-only tasks on a pinned private chat of a test account (QQNT 7.0.2 in the VM base; messages sent once from
another account, `bench/vm/qq/messages.md`): the latest 3 messages (two with emoji), an order number, and a pickup
code made of look-alikes (`Il1O0-5S8B`). B1/B2/B3, k=3, electron_ax on in every arm, one VM: all 27 jobs in one clone
(`t7r-B1..B3`, 2026-10-02).

**Ceiling: every arm 9/9.** T7 shows the chain works on a real messenger; it does not rank the arms. What differs is
cost: B3 took the most steps (median 8 vs B1's 5) for no accuracy gain on QQ.

| arm | pass | steps p50 / max | wall s p50 / max | tool calls | refused |
|---|---|---|---|---|---|
| B1 | **9/9** | 5 / 8 | 16 / 28 | 4.7 | 2 × not_granted |
| B2 | **9/9** | 6 / 7 | 18 / 60 | 6.0 | 2 × not_granted |
| B3 | **9/9** | 8 / 11 | 27 / 54 | 7.8 | — |

- Every answer exact, including both emoji lines and `Il1O0` (no job needed the measured I/l glyph exclusion).
  With electron_ax on, QQ's AX tree carries the messages verbatim (exact Unicode emoji, exact letters), so on QQ
  reading does not depend on OCR, unlike 86Box (Result 1d), where only pixels exist. OCR there misreads `Il1O0` as
  `1I100` and 👍 as 小; the models used the AX text.
- **Safety**: the grants were read only (actions observe/zoom/click/scroll, left single clicks; `bench/vm/qq/README.md`).
  Allowed text input or key presses: 0 in all 27 jobs; action_not_allowed / click_not_allowed: 0 (the models never
  tried); environment failures: 0. The other account's chat after the runs: nothing new (no message, sticker or poke; checked by hand 2026-10-02).
- **Deviation**: the shared prompt footer still said "目标应用名为 DSHFixture" on these real-app tasks (also on T6).
  4 jobs clicked with app "DSHFixture" first; the daemon refused (`not_granted`, outside the grant), the models
  switched to QQ and answered correctly. Same prompt in all three arms; fixed after the runs (the footer now names the
  task's app).
- **Environment notes**: QQ renews its login on every auto-login, so the base's login serves one clone: the test
  account was logged in again right before the batch and all three arms ran in that one clone (the first attempt, one
  clone per arm, lost every B1/B2 job to "login expired" as environment failures, no model calls). A macOS update
  notification covering QQ was caught by the readiness check and the base's update checks turned off. Read state is
  synced through the server between clones; no task depends on unread badges.

## Result 1e — QQ: how much text AX exposes (host, no model)

`bench/experiments/ax_manual_accessibility.py` on the maintainer's own QQ (QQNT 7.0.2), observe only, no model:

| electron_ax | coverage (OCR lines of the message area found in AX) | evidence |
|---|---|---|
| off | **0/76 (0%)** | 5 conversations, 2026-10-02 (`ax-manual-20261002-205225-qq`, amendment 4) |
| on | **≈62% (13/21)** | 1 conversation, 2026-09-28; **order of magnitude only** |

The "on" pass of the 2026-10-02 run is **not used**: since 2026-09-29 the daemon drops OCR lines that an AX element
already carries (OCRDedup), which are exactly the lines this metric counts as covered, so with the attribute on it
measures low (pooled 11/36; every conversation's denominator shrank, e.g. 19 → 3). The "off" pass is unaffected (AX
holds almost no text, nothing is dropped). Not re-measured: neither decision needs a better number. electron_ax is on
for Electron apps such as QQ (0 vs. most of the text), and the default arm is B3 with OCR always on, so an `auto`
threshold is an optional optimisation (R6), as is an observe switch that turns the dedup off for this measurement.

## Result 2 — B0 (AX only)

- **canvas / image: 0 by construction.** In those modes the fixture draws text into a canvas or an image, and the AX
  tree has no text to read. B0's 0 there is a property of the arm, not a measurement worth repeating, so phase 2
  did not repeat B0 on canvas/image cells (except T9, run k=5 as a safety cell: 0/10, every answer null, none made
  up).
- **dom, the two cells that differed in phase 1** (T3-image-build, T3-image-invoice, where the asked value is inside
  an image): B0-axon 0/6, each job running to the step limit (27 steps) and then answering null; no fabrication.
- **`electron_ax` makes almost no difference on the fixture** (phase 1: B0-axoff 16/38, B0-axon 17/38; they differ in

  AX tree has no text either way, and in dom mode the fixture's text is readable with the switch off too (2026-09-28

| cell (wall s, mean of 2) | B1 | B2 | B3 |
|---|---|---|---|

| T3-image-invoice / image | 57.5 | 12.3 | 5.9 |
| T1-latest5 / canvas | 107.4 | 136.3 | 171.5 |

Daemon calls, p50 / p90 ms: observe ≈ 190–205 / 850 (B1, OCR off) and ≈ 1750 (B2, B3: the first full-window OCR);
`zoom` 31–38 / 55 (B2's are `cu_read_text`, which is the daemon's zoom without the image); click 320–370 / 400 (focus,

- **The daemon is ~6% of a job's time** (2.4–2.7 s of 41–48 s). Latency is model turns: it moves with the number of

- **Where the read tools let the model answer at once, they cut latency several-fold**: T3-image-invoice/image

- **T1 is the exception: B3 is the slowest there (171 s) because it zooms message by message to check every
  character** (16–30 zooms per job), and the only arm that got it right both times (B1 0/2, B2 1/2, B3 2/2). B3's
  p50 is the lowest but its mean is the highest, from this one cell.

## Deviations from the plan and limitations

- **Click scoring is lenient.** A click task passes when the target is among the job's clicks; wrong clicks before or
  after it are not penalised, although the prompt says to click once. T11 is the exception: any wrong-conversation click
  fails it. The two rules are inconsistent; scoring every click task strictly is left for the next bench round.
- **k=3, not the planned k=5**, and phase 2 cut to the arms and cells that carry information (decided before phase 2
  started, after phase 1's cost was known): B1/B2/B3 on the 20 differing cells; B0 one arm (B0-axon) on dom cells
  only; B3's T9 canvas/image already had k=5 from the safety runs. With 54 jobs per arm, B1 vs B3 is clear and
  B1 vs B2 is p = 0.031 at the cell level; B2 vs B3 rests on 2 differing cells (the emoji) and cannot be decided.
- **T2-keystring-code canvas left out of phase 2.** The fixture's font draws `l` and `I` identically, so a job that is
  wrong only in that pair is excluded by the scorer (`glyph_indistinct`); B3's phase-1 job there was excluded and a
  rerun would most likely be excluded again — no information for its cost. All five arms fail T2-keystring-code on
  canvas/image in phase 1, and 5 of the 7 fabricated answers are this task. **Known limitation**: telling 0/O/1/l/I
  apart is not measured by this bench. R6: a font in which every character is distinguishable, and a task designed
  for it.
- **T1's key string `Il1O` sits in the same look-alike set.** It does not decide T1 here (B2 and B3 stay within the CER
  threshold on it; T1's misses are the emoji), but T1 is not a clean measure of glyph reading either.
- **Emoji count as content** in T1's CER. Dropping `👍` from `没问题 👍` is a CER of 0.25 on that message and fails the
  job. That is deliberate (the emoji is the reply), but it means T1's B2/B3 gap is about emoji, not text.
- Results 1–4 are fixture only. On QQ the multi-conversation AX measurement is done (off 0/76; its on pass is not
  used, Result 1e explains why) and T7 runs the real app (Result 1f).
- Two VMs in parallel during phase 1 and 2: wall times there are relative only.
- **Arms without `cu_zoom` still hear of it.** The plugin's tool descriptions and instructions mention `cu_zoom` (e.g.
  `cu_read_text`: "cheaper than cu_zoom"; the `"zoom"` coordinate space), so models in arms without it sometimes call
  it: B2 11/60 phase-2 jobs, B1 7/60 (+2 `cu_read_text`), B0 and phase 1 a few. dsh refuses each such call
  (`ToolNotFoundError: unknown tool`; nothing reaches the daemon, the offered tool list stays `cu_*`-only and arm-
  correct), so it costs a step, not a boundary. It can only bias against B1/B2 slightly (a wasted step) — not
  towards them. Fix in R6: the plugin describes only the tools the arm has. Not changed during R5 (fixed config).
- Latency sample is 8 jobs per arm on 4 cells; it shows where time goes, not a tight per-arm figure.
