# cu-runtime: design

English | [中文](DESIGN.zh-CN.md)

This is the design report of cu-runtime: how it works, why, and where to change it. It is written for maintainers and for an agent asked to understand or modify the project; the user-facing introduction is [README.md](../README.md), and the user guide (in Chinese) is [docs/desktop.md](desktop.md).

cu-runtime has two parts. The daemon (`CURuntime.app`, Swift) sees, reads, clicks and types only in the apps the person at the Mac approved, and makes every security decision. The dsh plugin bundle (TypeScript) adds the 电脑操作 mode, whose sessions get the `cu_*` tools and nothing else, and a plugin page that installs, updates and configures the daemon. The plugin never gets more than the daemon allows.

Building and testing: `npm run build` at the repository root builds the plugin (host, tools and page); `swift build` builds the daemon; `swift test`, `(cd plugin && npm test)` and `python3 -m pytest -q bench/tests` run the tests. `scripts/install-hooks.sh` installs the pre-push hook, which runs all of them plus gitleaks, semgrep, swiftlint and two privacy checks. A changed daemon reaches a Mac through the plugin page (its 守护进程 tab offers the update when the sources' hash differs); a changed plugin needs `npm run build` and a dsh restart.

Things that must change together: a settings change kind (`SettingsChange.swift`, the host's validator in `plugin/src/daemon/settings.ts`, the page's `plugin/src/client/settings/change.ts`); a refusal code (`Refusals.swift`, `KNOWN_REASONS` in `plugin/src/daemon/settings.ts`, `DAEMON_REASONS` and the texts in the page). Rules that must hold: a change that loosens anything needs the daemon's own owner check; a caller's word that it is verified never counts; no file path crosses the socket or a route; the model only ever sees what the daemon returns.

## Threat model

- **Defends against:** the model overstepping through its tools. That covers acting on apps outside the task's grant or on hard-denied apps, key chords outside the allowlist, clicks outside or behind the target's windows, and being talked by on-screen content into dangerous steps.
- **No approval without the dialog in daily use.** `grants.set` (a grant with no dialog) is refused unless the daemon's config file turns it on (`config_grants`), which only the bench does, in throwaway VM clones, and which only a bench build accepts: a release build does not start with it, nor with a state dir other than the default (Running). A bench build is signed with a certificate of its own, which only the VM base grants, so on this Mac it carries neither permission (Signing). So a client that reaches the socket cannot approve an app by itself; it can only ask through `access.request`, which shows the person the daemon's own dialog. Nor can it use approvals another client asked for: they are bound to that client's PID and executable (Connection authentication).
- **Where only one check stands: Notification Center banners.** A banner is drawn inside Notification Center's full-display window and is not among its app's top-level AX elements, so the window list side of the pre-action hit test, the occlusion flags and the composite do not see it: the model is shown the covered element as clickable. A click there is still refused, by the system-wide AX hit test alone (geometry `notification-banner`: `caught_by_ax_only`). After that refusal the lazy `occluded` marking (see Pre-action checks, step 7) flags the area, so the model does not walk into it again; it is not seen before the first refusal. Every other cover found so far is caught by both sides.
- **With bash in the same dsh (every everyday mode).** Everything above is about the `cu_*` tools: they reach only the apps a person approved. The bundle (Installable dsh bundle, below) registers them in one mode, 电脑操作, whose agents see no other tool (`onlyCuTools`, `exclusive`); the everyday dsh's other modes keep dsh's bash and file tools, as in dsh without this plugin, and bash does what dsh's sandbox lets it. dsh's sandbox limits writes only, so in every mode dsh's sandboxed bash and dsh's own file tools (`dsh-fs-sandbox`) can read the state dir's `token`; the sandbox is left as it is (documented, not changed). What a token holder can do: read the settings snapshot (no token, state-dir path or audit detail); make a change that tightens; ask for an app through `access.request`, which shows the daemon's dialog naming the asking process (executable and PID) and saying when it is that process's first request; start an owner check for a change that loosens, which a person at the Mac must pass and which cools down 10 s after a refusal. What it cannot: loosen anything, or approve an app without the person at the Mac. `grants.set` is off in daily use; approvals are bound to the client that asked; approvals are given only in a turn the asking client marked (`access.turn_start`, below), and a task's turns cannot be taken over by another client while the first one runs.
- **Not covered with bash:** (1) a session the user switches to dsh's `danger-full-access` mode runs bash unconfined: then only the daemon's own checks stand between bash and the daemon. This is left to the user on purpose: switching the mode is the user's decision and risk. (2) A program a command opens through LaunchServices (`open`) runs outside the sandbox. It can read the token and ask for an app under a task of its own (not under a running conversation's task, and not between turns); the dialog then names the asking process and says that it is its first request. The governed way to show a file in an app is `apps.launch` with `open` (an approved app, full mode, checked targets). (3) dsh's own process: code running in it (another plugin, a workflow script that escapes its isolation) has the plugin's PID, and with it the plugin's approvals. (4) bash can drive the GUI without cu (osascript, screencapture, CGEvents), as far as the TCC permissions of the process dsh runs under allow: do not give that terminal or app Accessibility, Screen Recording or Automation.
- **cu-std (an experiment).** `scripts/install-cu-std.sh` installs dsh's standard mode with a `screen` subagent that has only the cu_* tools, into a dsh home of its own (`~/.dsh-cu-std`, with its own copy of the API key), in a VM unless `--real-mac` is given. There bash is confined further: commands run confined can neither read the state dir nor connect to the socket (`scripts/cu-sandbox-runner`). Calls that leave the sandbox are asked by dsh's own escalation prompt (the gate leaves to it only a mode strictly wider than the session's current one; a `sandbox_permissions` naming the current mode, which dsh runs unasked, is a plain call to the gate), and every workflow call waits for the person's approval (`cu-exec-gate`); the gate's `confirm: after-screen` (every bash call once screen content may be in the conversation) is an option, off in cu-std since 2026-10-16 (P3). workflow is off in cu-std: its scripts run inside dsh's own process (gap 3 above). The top-level prompt tells the model not to use `open` in bash, which is advice, not a boundary.
- **What the keychain prompt approves.** Every signing asks for the login keychain password (Signing), so a daemon that holds this Mac's grants is installed only after the person at the Mac allowed it. The prompt approves whatever the package directory (the sources and `scripts/build-app.sh`) and the build cache (for the plugin page's install `~/Library/Caches/cu-runtime/build`: the copy of the sources, swift's scratch path, the output; for a build in a checkout, the checkout with its `.build/` and `dist/`) hold while codesign runs: a process that can write either of them chooses what the next install signs. `build-app.sh` keeps the rest of the way out of the directories dsh's sandboxed tool processes may write (`$TMPDIR`, `/tmp`): it assembles and signs the app in a 0700 work dir beside its output directory (`<CU_DIST's parent>/.build-app.*`: in the build cache or the checkout, which the prompt approves anyway), points `TMPDIR` (swift's and codesign's temporary files) and zsh's `TMPPREFIX` into it, and has xcrun skip its lookup cache, which lies in the user's temp dir. Before, the app was staged in `$TMPDIR`, where a binary swapped in between the copy and the signing would have been signed and installed.
- **Settings over the socket.** A client with the token can read the settings (`settings.snapshot`: no token, state-dir path or audit detail) and ask for one closed change at a time (`settings.apply`); it can tighten at once, but whatever loosens (an app off the deny list, onto the always list or raised to full, a looser access rule, a chord on or added, an always-list app whose signature changed approved again, content sent again, an app off the text-only list, coordinate targets, a higher input-source cap, Electron AX, a shorter retention, a reset or import that loosens) waits for the daemon's own owner check on this Mac, one at a time, with a 10 s cool-down after a refusal and never while an approval dialog is open; a client never says it is verified. The verdict is settled when it is given, and nothing is applied when the settings or the always list changed while the check was open; an import is previewed against the settings in force, and confirming it is refused (with the preview brought up to date) when they changed since the preview was shown. Files and folders (the log folder, import, exports) come only from the daemon's panels, chosen by the person at the Mac.
- **Does not defend against:** code that is already running as the same user. Such code can read any file this user can read and post CGEvents directly. The architecture cannot stop it, so it does not try. E2E runs happen inside throwaway VM clones, which contains that risk.

## Running

The daemon must be started by LaunchServices (`open`) or by a LaunchAgent, never spawned as a child process. macOS attributes TCC to the *responsible* process. A daemon spawned by node or sshd inherits that parent's permissions, not the ones granted to this app: TCC checks the app that started the chain (Terminal, dsh's desktop app, nothing over SSH), so the daemon's own Accessibility and Screen Recording grants would not apply, and it would act with whatever that app was granted. Started by LaunchServices, the app is its own responsible process.

```sh
scripts/build-app.sh                                  # dist/CURuntime.app, signed with the self-signed identity
open -n dist/CURuntime.app --args serve
scripts/cu-rpc.py runtime.ping
```

`build-app.sh` makes a release build. A bench build (`CU_BENCH=1 scripts/build-app.sh`, into `dist-bench/`; compiled with `-DCU_BENCH`, Info.plist `CUBench` true) is the only kind that takes `--state-dir` (`serve --state-dir DIR`, with `CU_STATE_DIR=DIR` for `cu-rpc.py`) or starts with the test-harness switches in `config.json` (`config_grants`, `debug_activation`, `debug_ime`, `debug_native_images`). A release build serves only the default state dir, reached by leaving the option out. It refuses to start with `--state-dir` in any form (the default's own path too) or with a switch on, and exits with a message naming it (a switch also on record in the audit log): otherwise any program of this user could start a second daemon with this app's permissions and approve apps without the dialog. The VM scripts deploy only `dist-bench/CURuntime.app`, and `build-app.sh` refuses to put a bench build into `dist/`, the daily path. Other knobs: `CU_SCRATCH` (swift build's scratch path, default `.build`) and `CU_DIST` (default `dist`, for a bench build `dist-bench`). Info.plist `CUSourceHash` is `scripts/source-hash.sh` of the sources built (`Package.swift`, `Sources/` and `scripts/build-app.sh`, which decides the Info.plist keys, the bundle id and the signing). `build-app.sh` calls every tool by its absolute path (swift through `/usr/bin/xcrun`), so it runs as `/bin/zsh -f scripts/build-app.sh` with only `PATH=/usr/bin:/bin:/usr/sbin:/sbin`, `HOME`, `USER`, `LOGNAME`, `TMPDIR` and `LANG`, and neither `PATH` nor `~/.zshenv` can swap a tool. It assembles and signs the app in a 0700 work dir beside the output directory (`<CU_DIST's parent>/.build-app.*`, for `dist/` the checkout; removed on every exit, signals included; a SIGKILL leaves it, and `scripts/find-release-builds.sh` lists an app left there), not in `$TMPDIR`, and points `TMPDIR` there for the tools it runs (Threat model). It prints `== sign` on a line of its own just before codesign runs and exits with status 3 when codesign or the check of its signature fails (a cancelled or denied keychain prompt, a locked screen), 2 when the environment is refused, 1 for its other checks.

The default state dir is `~/Library/Application Support/cu-runtime/` (0700). It holds:

- `daemon.sock` (0600)
- `token` (0600): regenerated on every start
- `audit/audit-YYYY-MM-DD.jsonl` (the default; the settings window's Logs page, or the plugin page through the daemon's folder panel, can move the log to a folder of the user's choosing, `<folder>/cu-runtime-logs/`, and sets how many days are kept)
- optional `config.json`: `{"allow_finder": false}` (the test-harness switches are for bench builds only, see above)
- `state-changes.json` (0600): system state this daemon has changed and not yet restored (see System state changes): Electron's `AXManualAccessibility` per app, and the keyboard input source. Written *before* each change, so the next start can undo it after a crash. A leftover `ax-manual.json` from older daemons is folded in.

The state dir and `audit/` must be real directories (not symlinks), owned by you, with mode `0700`; otherwise the daemon refuses to start. It creates them when they are missing, but never takes over or loosens an existing directory.

### Signing

`build-app.sh` signs with a self-signed code-signing certificate, found by exact name: `cu-runtime-signing` for a release build, `cu-runtime-bench-signing` for a bench build (`CU_SIGN_NAME` overrides the name; `CU_SIGN_IDENTITY` takes a SHA-1, or `-` for ad-hoc; several of the same name are refused). Each kind refuses the other's identity, by name or SHA-1 (exit status 2): this Mac's TCC grants pin the release certificate, and a bench build, which takes `--state-dir` and the test-harness switches, must never carry them; only the VM base grants the bench certificate (`scripts/vm-grant-base.sh`). So the certificate tells the kind, and `vm-lib.sh`'s `require_bench_app` deploys only an app the bench certificate signed. `scripts/make-signing-identity.sh [name]` creates an identity in the login keychain (once, in a Terminal on the Mac's screen: over SSH the keychain is locked and codesign fails with `errSecInternalComponent`); its key is on disk only encrypted with a one-time password, and its temp files are removed also when it is interrupted or terminated. It keeps a copy of the certificate alone (public; the key stays in the keychain) in `~/.<name>/cert.pem`, to check the identity against later, since listing the keychain again only shows what it holds now: `openssl x509 -noout -fingerprint -sha1 -in ~/.cu-runtime-signing/cert.pem` prints the release identity's SHA-1 in the form the plugin page shows it. That copy is only a convenience: any process of this user can rewrite it, and the script renames one already there to `cert.pem.replaced-<time>`, so a `cert.pem.replaced-*` next to it means it was rewritten (find out why before going by it). The reference same-user code cannot swap is the identity's `.p12` backup kept off this Mac (or a `cert.pem` kept off this Mac): `/usr/bin/openssl pkcs12 -in <the .p12> -nokeys -clcerts | /usr/bin/openssl x509 -noout -fingerprint -sha1` prints its SHA-1 the same way (it asks for the `.p12`'s password and writes no key). An identity made before the script kept it has none (run again, the script says so): take the certificate from the identity's `.p12` backup, `/usr/bin/openssl pkcs12 -in <the .p12> -nokeys -clcerts -out ~/.cu-runtime-signing/cert.pem` (it asks for the `.p12`'s password and writes no key; `/usr/bin/openssl` is the system's LibreSSL, while an OpenSSL 3 earlier on PATH, Homebrew's for one, cannot read the RC2-40 bag of such a `.p12` without `-legacy`). It is not marked trusted and need not be, so `find-identity -v` does not list it. The maintainer's release identity is `880B2E68…3B8D` (rotated 2026-10-21, replacing `3C6EB892…88C7`): its `.p12` is kept in an encrypted disk image and its password apart from it, and `~/.cu-runtime-signing/cert.pem` holds only the certificate, for convenience. The private key's access list does not trust `codesign` (since 2026-10-20): every signing asks for the login keychain password, so no process on the Mac can silently sign a look-alike app that would keep the TCC grants; answer Allow, not Always Allow (that adds `codesign` back). Identities made earlier trust `codesign`; docs/desktop.md 2.3 says how to remove it in Keychain Access without changing the key. The designated requirement pins the certificate (`certificate leaf = H"…"`), so TCC grants survive rebuilds. Ad-hoc signatures pin the cdhash and do not. `scripts/vm-signing-check.sh` proves both directions (see below). Builds made before 3ecf445 all carry this Mac's grants without hardened runtime: see Old builds below.

Every build is signed with hardened runtime (`--options runtime`) and no entitlements, and `build-app.sh` checks the flag after signing. The daemon needs none of the runtime's exceptions: no JIT or unsigned executable memory, only system libraries (so library validation passes without a team ID), no `DYLD_*` variable, no camera, microphone, location, contacts, calendars or photos, and no Apple events sent (it only receives the reopen event; apps and files are opened through LaunchServices). With it, the process that holds the TCC grants ignores `DYLD_*` variables (`open --env` could pass them) and takes no debugger.

**Old builds.** TCC keeps one row per permission for the bundle id `dev.cu-runtime.daemon`, holding the requirement of the app it was granted to, and that requirement pins the release certificate. So every bundle signed with it holds both grants wherever it lies: LaunchServices starts a copy in an archive or a forgotten worktree as readily as `~/Applications/CURuntime.app`. Only a hardened release build (Info.plist `CUBench` false, hardened runtime: what `build-app.sh` makes from 3ecf445 on) is fit to keep. Every release-certificate build that is not one still holds the grants: all builds made before 3ecf445, bench builds made then and the first R1 attempts (d4faaeb up to b0d4919, `CUBench` false) included. None of them has hardened runtime, so `DYLD_*` variables passed with `open --env` reach the process. Those from before R1 (no `CUBench` key) also serve any `--state-dir` and start with the test-harness switches, so any program of this user can start a second daemon that approves apps without the dialog; the first R1 attempts compared the `--state-dir` path as text, which a spelling through a symlink got past. An `~/Applications/CURuntime.app` installed from a checkout older than 3ecf445 is one of them: the plugin page's 守护进程 tab shows it as one to replace (it has no `CUSourceHash` and no hardened runtime), and 重新安装守护进程 there rebuilds and replaces it; `autoStart` does not open it. For the copies elsewhere there are two remedies; the maintainer decides which:

1. **Rotate the release certificate.** This is complete: granting a build signed with a new certificate replaces the requirement in the row, so every bundle signed with the old one loses both grants at once, copies in archives, backups and places nothing can find included. In Terminal, on the Mac's screen:

Press that only when the current SHA-1 is the one step 4 printed (`its certificate (SHA-1 …)`), which `openssl x509 -noout -fingerprint -sha1 -in ~/.cu-runtime-signing/cert.pem` also prints as long as nothing has rewritten that file since; then 重新安装守护进程 (the installed app does not satisfy the new identity's requirement). 2. **Delete every bundle `scripts/find-release-builds.sh` flags.** It lists every CURuntime.app it finds, by Spotlight and, for the places Spotlight skips, by find (this checkout and its `.claude/worktrees`, the `.claude/worktrees` of every other checkout Spotlight shows a `dist*/` build of, `~/Library/Caches/cu-runtime`, the host's staging names in `~/Applications`, `~/Archives`, `/private/tmp`, `$TMPDIR`, and any directory given, e.g. `~` to search everything), with its version, `CUBench`, hardened runtime and certificate: it keeps only hardened release builds signed with the current release identity and marks every other release-certificate bundle REMOVE; `--delete` removes those after "yes" on the terminal. It cannot vouch for copies in the Trash, in Time Machine backups, in hidden directories it does not search or on volumes it does not see, so this remedy is never complete. ## Connection authentication

1. The first frame on a connection must be `session.hello {"token": …}`, carrying the contents of the `token` file. Anything else, or a wrong token, gets error `-32001` and the connection is closed.
2. **The token is exactly as strong as the file's 0600 permissions.** It stops stray connections and clients left over from an old daemon. It does not stop code running as this user (see the threat model).
3. The peer's PID, the PID's version and executable path, taken from the audit token, are written to the audit log. They never grant anything, but **a person's approvals are bound to them**: approvals from the dialog belong to the peer that asked (`access.request`), and every use of them from another peer (another PID, another executable, a later process on the same PID — the audit token's PID version tells it apart — or an unknown one) is refused as `grant_owner_mismatch` (retry never), even after the answered dialog was settled during another client's call. Once that peer has exited (no process has its PID, the PID now runs another executable, or the PID is the asking connection's own with another version), its approvals end (`access.owner_gone`, audited): when dsh restarts and the same conversation goes on, the new process is asked again through the dialog, not refused. Config grants (the bench, `config_grants`) have no owner. A new process (a node one-liner included) has a new PID, or at least a new PID version, so the token alone no longer gives the use of someone else's approvals. A peer without an audit token (no PID version) never owns approvals.
4. At most 4 connections at a time; one more gets `-32010` (`too_many_connections`) and is closed. A connection that sends nothing for 5 minutes is closed (`idle_timeout`); time a request spends being handled does not count. Both are audited.

## Protocol

JSON-RPC 2.0 over the Unix socket. Each frame is a 4-byte little-endian length followed by the JSON body. Frames larger than 256 KiB get error `-32600` and the connection is closed.

A refusal is error `-32010` with a machine-readable `data.reason`, `data.retry` and `data.executed` (see Refusal classes). Every request also has a watchdog (30 s): if the worker has not finished by then, the client gets `-32003`. That means the **outcome is unknown** and the client should re-query state. For `act.*` the error carries `data.action_may_have_executed: true`, because the event may already have been posted: observe first, and never retry an action automatically. The daemon keeps serving, and external calls have their own deadlines (SCK 10 s, Vision 15 s, AX 1.5 s per message within a 3 s traversal budget). Every request, allowed or refused, produces exactly one audit line. For `act.type` the line records the text length, never the text.

| method | params | notes |
|---|---|---|
| `session.hello` | `token` | must be first |
| `runtime.ping` | | |

### Snapshots and clicks

Element and coordinate targets must carry the `snapshot_gen` they were read from. The daemon refuses a target if:
- its element changed (`stale_element`);
- its window moved or resized (`stale_coordinates`);
- it was not on the target app's window in that snapshot (`not_on_target_window`).

The daemon **cannot** detect a client that pairs old coordinates with a newer `snapshot_gen`. After any `stale_*` refusal, observe again and derive every target from the new snapshot.

Before a real click, the daemon also:
1. focuses the window under the point, so the click is not swallowed as an activation click;
2. waits for that window to hold still for 150 ms, because the system may reposition it on focus;
3. reports `window_changed_after_click` if the window changed right after the click anyway.

### OCR cache

OCR results are kept per window in window-local points (`OCRCache`), so consecutive observes only re-read what changed:
- A window that only **moved** is not re-read; its lines move with it.
- A **resized** window, or one whose last OCR failed, is read whole.
- Otherwise the window is compared with the last read on a 32 pt grid (mean absolute luma difference, threshold 2 on 0–255). Each changed cell widens to a full-width band, because text runs in lines, and a band grows over every cached line it touches. Only the bands are re-read.
- A re-read line with the same text in the same place keeps its id, so OCR element ids (`o<n>`) are stable across observes.
- OCR text that an AX element of the same app already carries, in the same place, is dropped in favour of the AX element (`deduped_against_ax`).

Offline corpus (60 images, `bench/offline/run.py --backend cu-runtime`, which runs `cu-runtime ocr-files`: the daemon's own OCR): CER 3.6%, key strings 74.5% (152/204), bbox hits 95.3%, identical to the reference `apple-vision` backend. Read in forced 96 pt bands (`cu-runtime-bands`, a pessimistic stand-in for band re-reads): CER 3.5%, key strings 76.0%, but bbox hits 90.8%, because lines cut at band edges get partial boxes.

VM numbers (2026-09-29, `bench/experiments/ocr_cache.py`, 1440×900 @2x, 12 lines): unchanged p50 ≈ 0.14–0.24 s, one changed line p50 ≈ 0.31 s (≈10% of the window re-read), whole window ≈ 0.75 s. The first OCR after start is still ≈ 2.5–3.4 s despite the start-up prewarm.

### cu_zoom

`zoom` crops the same occlusion-blocked composite as the overview, from a fresh capture, so it never shows more of other apps than the overview does. Rules:
- It needs the `snapshot_gen` of an observe that produced an image. The granted windows under the rect must be unchanged since then, and no granted window may have appeared there (`stale_coordinates`).
- The crop is native resolution up to the 640k px budget, then scaled down; `magnification` is its detail relative to the overview. A rect that would show no more detail than the overview is refused (`zoom_not_magnifying`).
- An element target zooms on its frame plus 16 pt.
- OCR lines come from the OCR cache (they are data, under `untrusted_observation`). To click something seen in a zoom, use `point{space: "zoom", zoom_id}`: the daemon maps it back and checks it against the zoom's snapshot like any point.
- No per-task limit in the daemon; every zoom is audited. A budget per task belongs to the plugin (R4).

### Waiting for windows

- Before any wait, observe asks AX where each granted app's windows are (WindowPresence: not_running, hidden, minimized, no_windows, visible) and returns the ones without a window to show as `app_states`. Only visible apps, and apps this daemon launched moments ago, are waited for (window wait, electron_ax settle); a minimized QQ used to cost 8 s of waiting for nothing (2026-10-09). An app that refuses AXManualAccessibility (a native app) is not asked again until it relaunches.
- A granted app that is running but lists no window has usually just launched or been activated: the window server listed new windows up to ~2 s late. `observe` polls for up to 2.5 s instead of returning nothing. An app still windowless after that (all windows closed, a menu-bar app) is remembered by pid and not waited for again until it shows a window.
- An app this daemon launched (`apps.launch`) is waited for, up to 2.5 s within 10 s of the launch, until macOS reports it as running. Apps launched by anyone else are not.
- At start the daemon warms up the window list, SCK and Vision in the background (`runtime.prewarm` in the audit log).
- For display (observe, zoom), the Dock's bar (OverlayPolicy) is read over AX with a 0.25 s timeout and reused for 0.5 s; if the Dock does not answer (it did not while animating a launch), the last known frames are used. Allow/refuse decisions never use these: see Pre-action checks.
- The first OCR after start still takes ~2.5–3.4 s. A start-up Vision prewarm (even window-sized, mixed zh/en, on OCR's own queue) did not remove it. Bench runs and the plugin (R4) do one warm-up `observe` before timing or starting a task.

### System state changes

Some things this daemon changes outlive a single action or reach beyond the granted app's content: Electron's `AXManualAccessibility` (changes the target app) and the keyboard input source (global: every app sees it). They go through one mechanism (`SystemStateChanges`):
- a policy per change: `leave` (never change it), `ask` (only after a person approved), `takeover` (for the task, then restore);
- a ledger entry (`state-changes.json`) written **before** the change;
- restores in layers: when no active grant wants the change any more (the plugin revokes at `turn/end`; expiry is noticed on the next request), on SIGTERM/SIGINT, and at the next start after a crash;
- an audit line for every change and every restore (`ax.manual_accessibility`, `system.input_source`).

### electron_ax

Electron apps expose their web content to AX only when `AXManualAccessibility` is set. For QQ (QQNT), visible-text coverage went from 0 to about 60%. Setting it changes the target app, so:
- it is an explicit per-grant opt-in, and every switch (on or off) is audited;
- it is applied lazily on the first observe;
- after switching it on, the daemon waits for the AX tree to settle before reading (`AXSettle`: the node count must leave its pre-switch baseline and hold still; timeouts are reported, never hidden);
- it is switched back off when no active grant wants it, on SIGTERM/SIGINT, and at the next start via the ledger (System state changes). Restarting the app is still the only full reset. `electron_ax: true` is the `takeover` policy of this change, `false` is `leave`.

### Actions

- **AX first.** An `element_id` click on an AX element that supports AXPress is an AXPress: no activation, not affected by what covers the element. `act.set_value` sets AXValue, `act.ax_action` performs an allowlisted action. The AX path still checks the grant, the hard-deny halt and the element's staleness. Results say `via: "ax"` or `via: "event"`.
- **Real events otherwise**, after every pre-action check below: points, OCR elements, right/middle buttons, double and triple clicks (`kCGMouseEventClickState` 1…n), scrolling, drags (down, 12 dragged moves, up), typing and key chords.
- **Typing:** text goes out as Unicode keyboard events (no input method in between, so Chinese arrives as typed) in chunks of at most 20 UTF-16 units, never splitting a character. Line breaks and tabs are Return and Tab presses. Before every chunk the target must still be frontmost; if it is not, typing stops with `focus_lost`, and `steps_posted` says how far it got.
- **Pasting** (`act.type` with `strategy: paste`, P4 2026-10-16, after the official cua-macos provider): the text goes through the clipboard and ⌘V, so no input method can swallow it and no input source changes. The clipboard is saved first (every type of every item, at most 32 MB, else `clipboard_too_large` and nothing is pasted) and put back once the app had 0.3 s to read it, unless something else wrote the clipboard meanwhile (`clipboard_changed`: left alone). With an element target the field is read back (`verified`). Same floor as typing: full mode, password fields refused, the app frontmost (`focus_lost` restores the clipboard). The plugin suggests it when a typed text did not arrive.
- **Screen lock** (P5, 2026-10-16): with macOS locked (`CGSSessionScreenIsLocked`), observe, every action and `apps.launch` are refused `session_locked` (retry never: the person unlocks, the model observes again) before anything happens. An unknown lock state is not refused.
- **Key chords:** the modifiers are pressed as real keys (down in order, up in reverse), each event carrying the flags held at that moment.
- **Activation:** `NSRunningApplication.activate()`, followed by the usual check that the app is frontmost within 500 ms. Measured in the VM (`bench/experiments/activation.py`, 20 trials each): `running_application` 20/20 with another app in front and 20/20 when the target was hidden; `ax_frontmost` 20/20 and 0/20; `ax_raise` 0/20 and 0/20 (it raises a window but does not activate the app). `activation_method` in config.json overrides the default.
- **The pointer's own window** is not part of the window order. In the VM it is a real on-screen window at the pointer position, and it made the point the mouse last rested on look covered. Only a window that is **owned by the Window Server and** at the cursor level is left out: any app can put a window at that level, and such a window still covers (geometry suite `occlusion-cursor-level`: 6/6 refused by the window list itself; with the old layer-only rule only the AX hit test caught them).
- **No credentials are typed.** `act.type`, `act.set_value` and `act.key` are refused (`secure_input`, retry `never`, "ask the user to enter it themselves") when the target element, or else the app's focused element, is a password field (AXSecureTextField as role or subrole), or when the system's secure event input is on. Checked at action time, before and after activation. Clicking a password field is allowed. VM: typing, setting a value, typing and a key press while it is focused: 4/4 refused, the field stays empty.
- **Input methods.** With Pinyin selected and nothing composing, typed text arrives exactly (3/3). While the field holds an uncommitted composition (keys n, i: "ni" with candidates), every typed character was swallowed (3/3) although the events were posted. With an element target, `act.type` therefore reads the value back and reports `verified: true|false`; a false means the text did not arrive (`bench/experiments/ime.py`). What `act.type` does about it is under Input methods below.

### Input methods

In order, for `act.type`:
1. **Set instead of type** where that equals typing: an element target whose AXValue is settable, an empty field (typing inserts at the caret, a set replaces everything), no line break or tab, not a password field. The value is read back; if it does not match, it is set back to empty and typed instead (`set_value_fallback`). This bypasses the input method and changes no system state. Chromium fires its `input` event on an AX set: the DOM value, the page's own copy and a send button that listens to `input` all followed, 6/6 (input and textarea, `bench/experiments/ime_probe.py`). Whether a given app reacted is not something the daemon can judge in general: the result says `app_reaction: "not_checked"` and the plugin tells the model to check with the next observe.
2. **Otherwise the grant's `ime_policy`**, if the current input source is an input method (keyboard layouts need nothing: Unicode events pass through them):
   - `leave`: type as is; the result has `ime: "left"` and an `ime_warning`;
   - `ask`: refused `ime_switch_needs_approval` (nothing typed) until `ime.approve`; `call` scope restores right after that input, `task` scope when the task ends;
   - `takeover`: switch to the ASCII layout the system pairs with the input method (`TISCopyCurrentASCIICapableKeyboardLayoutInputSource`; in the VM base that is British, not ABC) and restore when the task ends.
3. **Never switch under a composition.** Switching would commit or drop what the user is composing: `ime_composing` (retry `after_observe`: cancel with Escape or let the user finish, then observe). Detection (`ime_probe.py`, VM, macOS 26): Pinyin's candidate panel is a window of the **app's own process** at the Dock window level (20) while a composition is open, 6/6, and absent when idle, after Escape and after committing, 9/9. AX has no marked-text attribute (the value holds "ni" like typed text; the attributed string carries only font and colour). For input methods other than the measured Pinyin (`com.apple.inputmethod.SCIM.*`), no panel means `ime_composing: "unknown"`, not false.
4. **Restore only what is still ours:** a restore selects the original source only if the current one is still the one the daemon set; if the user switched since, their choice stands (`restore_skipped`, audited).

Measured in the VM:
- The daemon, started through LaunchServices, can select input sources with `TISSelectInputSource`: 6/6, 1–12 ms, verified by reading the current source back (TIS calls are made on the main thread).
- End to end (`bench/experiments/ime_policy.py`, 7/7): takeover types exactly and restores on revoke; a composition is refused and nothing is typed; ask refuses, then after `ime.approve` types and restores right after; leave warns and changes nothing; SIGTERM restores; after SIGKILL the source stays switched with the ledger entry, and the next start restores it; an empty field is set through AX with no source change at all.
- Fixed on the way: the signal handler used to wait for the worker on the main thread while the restore needed the main thread (TIS), so SIGTERM skipped the restore until the shutdown timeout. The shutdown now runs off the main thread.
- **Not verified:** "Automatically switch to a document's input source". Written with `defaults write com.apple.HIToolbox AppleGlobalTextInputProperties -dict TextInputGlobalPropertyPerContextInput -bool true` plus relaunching Finder and the fixture, the VM still behaved globally (Finder showed the source selected in the fixture). If per-document mode is really on, the likely effect is a skipped restore (another app in front shows its own source), which is audited as `restore_skipped`.

Defaults: the plugin's `imePolicy` is `ask` on a real Mac (a switch reaches other apps) and `takeover` in the VM bench arms.
- VM results (`bench/experiments/actions.py`, both display configs): element clicks through AX 9/9, through events 9/9, point clicks 9/9, double click, right click, a 45-character mixed Chinese/English text typed exactly, a two-line textarea, cmd+A then typing replaces the text, AXValue set, scrolling both ways, a drag landing 0 pt off, and a moved window's elements refused as stale by both paths with nothing reaching the fixture.

### Refusal classes

Every refusal carries `data.retry` (`Refusals.classes`; a test fails if a refusal in the sources is unclassified):

| `retry` | meaning | client |
|---|---|---|
| `after_delay` | refused before anything ran, for a transient reason (`overlay_state_unknown`, `activation_failed`, `window_focus_failed`, `too_many_connections`, `launch_failed`) | may resend the same request a few times, after a short delay |
| `after_observe` | refused before anything ran because the screen is not what the snapshot said (`stale_*`, `hit_test_failed`, `not_on_target_window`, …) | observe again and build a new request; never resend |
| `never` | refused by policy, or the request is malformed (also `ime_switch_needs_approval` and `ime_switch_failed`, which the plugin answers by asking a person or by resending with `ime_policy: leave`; nothing was typed) | do not retry as is |
| `outcome_unknown` | the action may have happened in full or in part (`action_failed`, `focus_lost`, `request_timeout` of an `act.*`); `data.action_may_have_executed: true` | never retry automatically: observe first |

The plugin (R4) retries automatically only `after_delay`, a bounded number of times. `data.executed` is `false` for the first three classes and `null` (unknown) for the last.

### Pre-action checks

These run in order for every `act.*`. The first failure refuses the action and is audited.

0. **An app named by its display name** ("DSHFixture" instead of `dev.dsh.bench.fixture`) is resolved first, among the task's granted apps only, and only if exactly one matches (localized name, bundle display/short name or .app file name; case and surrounding space ignored). Several matches are refused as `app_name_ambiguous`; no match stays as sent and is refused as `not_granted`. The daemon never looks up the names of apps outside the grant, so this cannot widen it, and the resolved bundle ID still goes through the checks below. The audit keeps `app_name` and `app_resolved_from_name`. (R4: every `not_granted` was the model using the display name.)
1. The grant exists and has not expired.
2. The app is not hard-denied (defense in depth), and the grant covers it.
3. The chord parses and passes the allowlist (see below).
4. Every target is an `element_id` from a live snapshot, or a point that declares its `space`. In R1 there are no snapshots and no image mapping, so only `space: "screen"` points pass.
5. **A hard-denied app is not frontmost.** If one is (for example, a link in the target launched a terminal), every action stops. The daemon does not quietly pull the target back over it.
6. **Activate, then verify:** the app must become frontmost within 500 ms.
7. **Hit test:** at each point, the topmost window in the window list **and** the system-wide AX hit test must both name the app.
   - **Safety premise:** the AX hit test follows the window server's click routing, so it names an invisible (alpha 0) window of another app that takes clicks, which the window list skips. If AX gives no answer, the action is refused (fail closed). One exception: an app that does not implement the AX hit test at all (`kAXErrorNotImplemented`, which WeChat 4 answers for every point, 2026-10-14) is decided by the window list read again with invisible windows counted, so an alpha-0 window of another app over the point still refuses; such clicks are audited as `hit_test: window_list_only`. Any other AX failure still refuses. Not covered by the fallback: a window that lets clicks pass through looks covering to it, so the click is refused (safe side). The geometry suite keeps `occlusion-invisible` (overlay takes clicks: every click refused; with the AX check removed, 6/6 were intercepted) and its click-through control `occlusion-invisible-clickthrough` (every click lands) as permanent regressions, so a macOS change to either side shows up.
   - A click refused because the two disagree carries `data.intercepted_by` (the interceptor's bundle ID, or `unknown`). The daemon remembers that area and flags elements in it as `occluded` (with `intercepted_by`) in later observes, until the window list changes. No per-element AX hit test runs during observe.
   - The Dock's visible area is read fresh for this check. If the Dock does not answer (it does not while animating a launch), the refusal is `overlay_state_unknown`: retry in a moment. Reused or last-known Dock frames are only used for display (occlusion flags, the composite).

### Key chords: allowlist

A blocklist would always leak. Users define their own shortcuts, third-party apps register global hotkeys that fire whatever app is frontmost (QQ/WeChat screenshots, Raycast, Alfred), and F-keys change meaning with the fn-lock setting. So the rules are:

- A key with no modifier, or with only ⇧, is **allowed**. That covers letters, digits, punctuation, return, tab, escape, arrows, delete, Home/End/PgUp/PgDn and space.
- A chord with any of ⌘ ⌃ ⌥ fn is allowed **only** if it is on this list: ⌘A C V X Z, ⌘⇧Z, ⌘F G W N S Q, ⌘⌫, ⌘L (a browser's address bar) and ⌘⇧T (2026-10-14), and ⌥ or ⌘ plus an arrow key. Add to the list when a real task needs more.
- F1–F20 are refused, with or without modifiers.

The old R1 blocklist now lives in the tests as an acceptance set (`legacyBlockedChords`): every chord on it must be refused. By construction the allowlist also refuses chords that affect other apps, such as ⌘⌥H.

### Hard-deny list

The table is in `Sources/CURuntimeCore/HardDeny.swift`. Each entry records how its bundle ID was verified:

- **`localInfoPlist`**: read from the app on this Mac.
- **`upstreamSource`**: read from the app's own source repo: iTerm2, kitty, WezTerm, Alacritty, Ghostty, Zed, Python Launcher.
- **`unverified`**: taken from a Homebrew cask: Cursor, Android Studio, Sublime Text, JetBrains.

Vendor namespaces are matched **by whole dot segments**: `com.jetbrains` covers `com.jetbrains` and `com.jetbrains.pycharm`, but not `com.jetbrainsfoo.app`. This covers Ghostty's `.debug` build, Sublime Text IDs that carry the major version, and all of JetBrains. Zed's release channels differ by a `-Suffix`, not a dot segment, so all four are listed exactly.

Finder is not hard-denied. It is config-gated instead: it needs `allow_finder` in the daemon config and a `config`-sourced grant.

Upstream code: the prototype ran on `AzaiSakura/dsh-computer-use`'s daemon, and `legacy/` keeps its patches to that daemon for history only; the current daemon reuses none of its code. Any later port (e.g. `AXTreeDiff`) must carry its MIT notice.

## Plugin (R4)

`plugin/` is the dsh plugin: the `cu_*` tools. It only connects to the daemon's socket and never spawns the daemon as its child (TCC would credit node instead of the app); with `autoStart` (the bundle's mode, cu-std) it opens the installed app through LaunchServices, only a release build the host verified (Installable dsh bundle, below), and otherwise says where to start it when it cannot connect. Every policy decision stays in the daemon. Per dsh session (one task):
- the first tool call grants the configured `apps` (source `config`, `electronAx` set explicitly) and runs one warm-up observe; the grant is revoked at `turn/end`;
- element ids are stable across observes (`e…`/`o…` from each element's key, a hash of role, identifier, text, frame and window). The plugin maps them to the latest snapshot, so after the first `cu_observe` only changes are listed; a changed element gets a new id, and an old id is unknown rather than re-pointed;
- only refusals with `retry: after_delay` are retried (3 times, after 0.5/1/2 s); every other refusal goes back to the model with what happened and what to do next;
- with `appApproval: none` (the default: bench, headless), `cu_request_app(app, mode, reason)` goes to the daemon's approval flow, which refuses it without a dialog. With `appApproval: dialog` (the bundle's mode, cu-std) there is no `cu_request_app`: a call refused before anything ran because the app has no approval (`not_granted`, `no_grant`, or `cu_observe` with `app`) or its read mode does not allow it (`needs_mode: full`) first takes an approval that already covers it (a silent `access.request`); else the user is asked at once for the full mode (`access.request` interactive with the call's `justification`, then `access.status` every second until a person answers), and the call is sent again. Nothing is asked under the session's dsh approval policy `never` (or without the approval service), or for an app whose dialog failed this turn (refused, timed out, over the daemon's limit): the daemon's `approval_refused_earlier`, `approval_limit`, hard-deny and deny list still decide. The `justification` field and the matching system-prompt text exist only in this mode, so the bench's tools are unchanged;
- `exclusive` (default true): every cu_* tool refuses while the model can also see any non-cu_* tool (bash, files, run_code…), so computer use never runs next to a shell even if a profile is misconfigured;
- `onlyCuTools` (default false; the installable bundle's mode below): the row sits inside an agent preset, and each of that preset's agents is denied every tool the host gives it, one name at a time, before its first step: at `agent/created`, or for a new session's agent moved into the mode when the person picks it, at `agent-preset/selected` and `turn/start`; again before every step for a host tool added since. A tool dsh will not deny there (one another row of the same preset registers) stays visible and `exclusive` refuses the cu_* calls. It cannot be combined with `hideFromRoot`;
- `imePolicy` (default `ask`) and `imeApproval` (`call` by default, or `task`) go into the grant. On `ime_switch_needs_approval` the plugin asks `ctx.approval` (dsh only has one-shot approvals, so the scope is config), calls `ime.approve` and sends the text once more; refused or headless, it sends it with `ime_policy: leave` and says the source was not switched. `ime_switch_failed` gets the same downgrade;
- screen text is framed as untrusted observation, and a system-prompt section states the rules (element ids first, declared coordinate spaces, a line break submits, no credentials).

dsh 0.1.5 does not let a plugin drop old images from the conversation history (`agent/request` cannot mutate messages), so long tasks accumulate one image per observe; `cu_observe({image: false})` skips it.

(cd plugin && npm run build && npm test)          # build: the host tsc, then the plugin page (scripts/build-client.mjs)

The repository root is also a dsh bundle (`package.json`, `cordis.patch.yml`, `locale/`, `icon.svg`): dsh's 添加插件, or `dsh plugin --profile <p> add`, installs it into a profile of the everyday dsh home. It adds one mode (agent preset), 电脑操作, and the plugin page that manages the daemon and its settings; it changes nothing in the other modes:
- the package root (`cu-runtime`, `plugin/lib/host.js`) is one top-level row, `cu-runtime-host`, with no tools. It stops dsh 0.1.5 (no profile context) with the supported range (from 0.2.1-alpha.4 on, dsh itself refuses a release outside `engines.dsh`), and serves the plugin page (dsh mounts a package's page only on a top-level row named as the package);
- the preset's plugins are the persona (`profiles/presets/cu-desktop`, the name kept from the retired cu-desktop profile) and the tools row, `cu-runtime/tools` (`plugin/lib/index.js`), with `apps: []`, `appApproval: dialog`, `electronAx: true`, `imePolicy: ask`, `imeApproval: call`, `restoreFocus: true`, `autoStart: true` and `onlyCuTools: true`. The cu_* tools are registered inside the preset, so only its sessions see them, and those sessions see nothing else (checked end to end in dsh 0.2.1-rc.2 web against a capturing model endpoint: 14 cu_* tools in this mode, none in 标准模式). cu-std and the bench load `plugin/lib/index.js` by path;
- `@deepseek-ai/dsh-tools` and `@deepseek-ai/schemastery` are peer dependencies: the running dsh's copies;
- `cordis.patch.yml` is generated from `profiles/bundle/cordis.patch.yml.in` and `profiles/presets/cu-desktop` by `node scripts/gen-bundle-patch.mjs`; `plugin/tests/bundle.test.mjs` checks it is current, the manifest, and that the packed package holds the built plugin and the daemon's sources.

Adding a plugin needs pnpm: dsh's 添加插件 and `dsh plugin` run the `pnpm` on dsh's PATH. A dsh installed with npm brings none, so run `npm i -g pnpm` first; without it 添加插件 shows only "exit code 127" and no other output (dsh's log has `spawn pnpm ENOENT`). The desktop app (DeepSeek Harness.app) brings its own. Updating the bundle is removing it on the plugin page and adding the new package, which needs pnpm as well; the plugin page says so at its foot.

The plugin page talks to the host row through owner-only routes, `POST api/cu-runtime.<op>`, every one but `settings.apply` without parameters (`plugin/src/daemon/`): `status` (installed app, version, whether it was built from this package's sources by `CUSourceHash`, signature, signing identity and its certificate's SHA-1, whether that identity is the one the host last signed with or created, running, permissions from a recent self-check, Command Line Tools, SSH, the install task, and who else holds the host's lock), `install`, `cancel`, `permissions`, `start`, `stop`, `restart`, `selfcheck`, `clt` and `acceptIdentity`. In dsh 0.2.1-rc.2 web the routes were checked with curl and an owner cookie, and the page separately; the Electron app is not checked yet, and headless has neither. Install builds the daemon in `~/Library/Caches/cu-runtime/build` from a copy of the package's `Package.swift`, `Sources/`, `Tests/` and `scripts/` (the package directory is never written), signs it with `cu-runtime-signing` (created if missing; the keychain asks the person at the Mac to allow the signing, and a cancelled or denied prompt fails the install; ending codesign does not close its password dialog, so after a signing failure, or a task that ended while signing, the page says one may still be open and is closed with 拒绝 (Deny)), checks that the new app is a release build (Info.plist `CUBench` false: a bench build never replaces the installed app) and satisfies the designated requirement, stops the running daemon, replaces `~/Applications/CURuntime.app`, starts it with `open -g` and runs a self-check. If neither the new app nor the old one can be put in place, the failure names where both were left. It refuses an SSH session and a Mac without the Command Line Tools (`clt` opens macOS's installer). The requirement is the bundle id and the certificate of the one local identity named `cu-runtime-signing`; with several of that name, install, start, restart, permissions and selfcheck all refuse (`identity_ambiguous`). The page's start, restart, permissions and selfcheck launch the installed app only if it satisfies the requirement and is a release build (an installed bench build shows as a signature mismatch and is refused, `not_release_build`); the tools row's `autoStart` applies the same check before it opens the installed app (`open -g`; `plugin/src/autostart.ts`): an app that fails it is not opened, and the call is refused with `the installed CURuntime.app is not a release build the plugin verified: <code>` (`not_installed`, `identity_missing`, `identity_ambiguous`, `not_release_build`, `signature_mismatch`, or `internal`) and the hint to install or update it on the 守护进程 tab, the same answer for the 30 s after it. `permissions` opens one System Settings pane per call, Accessibility, then Screen Recording once a self-check (`selfcheck`, 检查权限) shows Accessibility granted, and never resets a grant. The host keeps the SHA-1 of the identity it last signed with successfully or created in `~/Library/Caches/cu-runtime/known-identity`; while that file is missing, unreadable or malformed, the SHA-1 it knows is the installed `~/Applications/CURuntime.app`'s leaf certificate's, read display-only (`codesign -d`, never signing; the page labels it 已安装应用的证书 SHA-1, Installed app's certificate SHA-1, instead of 上次使用的证书 SHA-1), and nothing is written to the file except after a successful sign, a creation or an accept. When the one `cu-runtime-signing` identity is not the one it knows (a look-alike of the same name put in its place, for example), install refuses (`identity_changed`) until the owner accepts the current one on the page (确认当前证书, `acceptIdentity`, logged with both SHA-1s); until then the page also holds start, restart, permissions and selfcheck, so no permission goes to an app of that identity. `acceptIdentity` accepts only the identity the page was shown: when the certificate changed again since, it refuses (`identity_changed`), and the page reads the status again after it either way, so the new SHA-1 is what it then shows. Before accepting, compare: the page shows both SHA-1s in openssl's form, and the current one must equal the fingerprint of the certificate in the identity's `.p12` backup kept off this Mac (or of a `cert.pem` kept off this Mac), the reference same-user code cannot swap: `/usr/bin/openssl pkcs12 -in <the .p12> -nokeys -clcerts | /usr/bin/openssl x509 -noout -fingerprint -sha1`. The copy `scripts/make-signing-identity.sh` kept on this Mac, `openssl x509 -noout -fingerprint -sha1 -in ~/.cu-runtime-signing/cert.pem`, is only a convenience: any process of this user can rewrite it, so a match with it does not rule out a look-alike, and a `cert.pem.replaced-*` next to it (the script renames an existing `cert.pem` so when it makes an identity again) means it was rewritten: find out why before accepting. `security find-identity` cannot tell: it lists whatever the keychain holds now, the same source the host reads, and with `-v` it does not list this untrusted identity at all. One install runs at a time, across dsh processes too: while another dsh process, or an earlier load of the package in the same process (still finishing after an update), holds the lock, the status names its pid and since when (`busy`), and the page holds its buttons and reads the status every second. Each operation is logged, with its outcome and a failure's message, to `~/Library/Caches/cu-runtime/host-actions.log`. The status holds no token, audit or screen content.

The daemon's settings reach the page through the same row (`plugin/src/daemon/settings.ts`): `settings.snapshot`, `settings.apply`, `settings.cancelVerify` and `settings.action.<name>` for `choose_log_directory`, `use_default_log_directory`, `choose_app`, `export_settings`, `export_audit`, `import`, `import_confirm` and `reveal_log`. They call only the daemon's `settings.snapshot`, `settings.apply {change}`, `settings.cancel_verify` and `settings.action {name}`, each over one connection to the socket in the fixed state dir, closed afterwards, without starting the daemon; only while the installed app the host verified (a release build satisfying the designated requirement, with hardened runtime) runs (`not_running` otherwise), and not while the install task stops, replaces or starts it (`busy`). `settings.apply` is the one route that reads its body: `content-type: application/json`, the header `x-cu-runtime-page: 1`, at most 4096 bytes, and `{"change": {...}}` with exactly one change as the daemon decodes it (a known `kind` and exactly its keys, the offered values, the bundle ID, note, chord and task ID limits); anything else is HTTP 400 `bad_request` and reaches neither the daemon nor the gate, and what is sent is a fresh object of the checked fields. The snapshot keeps only the top-level keys the page shows; a daemon refusal the page knows keeps its reason (`verify_cooldown` with `data.until`), any other is `daemon_error`, messages clipped to 300 characters. The daemon checks every change again and verifies the person itself (Touch ID or the password) before a change that loosens anything; the host never opens or reveals a path from the page or the daemon. No other route forwards a daemon request.

The plugin page has a tab bar (`plugin/src/client/settings/shell.ts`; dsh's SegmentedTabs where the running dsh has it): 守护进程 (Daemon), the page described above and the one shown first, then the daemon's settings in the settings window's order, 概览, 档位与默认, 应用名单, 快捷键, 隐私与审计, 行为与模型 and 日志. The settings tabs read `settings.snapshot` only while one of them is shown: every second while a change waits for the owner check or one of the daemon's panels is open on the Mac, every 10 s otherwise, and at once after each change, action or cancel. A change waiting for Touch ID or the login password shows a banner on every settings tab with what it does and 取消 (`settings.cancelVerify`), and holds every control that changes something until it is settled; the settled outcome is shown once. 概览 shows the three permissions, the new-session default, the approvals in effect with their time left (撤销 per task, 全部撤销) and the recent refusals. 档位与默认 sets the access rules (`access.set`). 应用名单 keeps the always list (add with a mode, change the mode, re-approve an app whose signature changed, remove) and the deny list (add with a note, remove), with apps picked in the daemon's app panel (`choose_app`), and shows the hard-deny floor no setting changes. 快捷键 turns built-in chords off and on and adds or removes custom ones, typed rather than recorded. 隐私与审计 sets what is sent to the model (`privacy.set`), the text-only apps and whether the clipboard is emptied when a turn starts. 行为与模型 sets the behavior fields, resets the settings after a confirm, and exports and imports them through the daemon's panels: an imported file is shown as what it changes and what it loosens, compared with the settings in force, before it is applied. 日志 shows the log folder, which changes only through the daemon's folder panel or back to the default, sets the retention, exports the last 7 days, shows the folder in the Finder and lists the recent settings changes. The page never decides what loosens; the daemon does, for every change. The settings window (`cu-runtime settings`) has the same pages.

The 守护进程 tab also shows the mode check (`plugin/src/daemon/mode-check.ts`, routes `modeCheck` and `modeCheckRefresh`, each answering `{ok: true, result}`): every profile of the running dsh's home (`DSH_HOME`, default `~/.dsh`; no other home) is checked through `dsh --profile <p> --dump-config` (a profile of dsh's Electron app through its files): the cu_* tools in the bundle's mode only, in one row, with `onlyCuTools` on, `appApproval: dialog` and `exclusive` not off, and no other computer-use plugin in any profile. A result is cached for 60 s; 重新检查 runs it again. About 10 s after the host row loads it runs once, and each failing line goes to dsh's log as a warning, `cu-runtime: mode check: profile <p>: …`.

Not yet: the mode's settings are not on dsh's plugin page (a preset's rows cannot be configured there). ## Tests

Hooks are not cloned, so run `scripts/install-hooks.sh` once **on every machine**. It sets `core.hooksPath=scripts/hooks`, and the pre-push hook refuses to push until `.git/info/private-patterns` holds your private strings. Before every push the hook runs:
- Swift tests and pytest;
- gitleaks over the full history, semgrep, and SwiftLint (errors only);
- privacy checks: generic patterns in tracked files, GitHub noreply addresses for every pushed commit's author and committer, and your own private strings from `.git/info/private-patterns`. That file is never pushed.

Audit reports live in `docs/audits/`.

**Measurements depend on daemon behaviour.** A measurement script reads what the daemon returns, so when that
behaviour changes (filtering, deduplication, geometry), re-validate the measurement before trusting it. The QQ AX
coverage script was written before OCRDedup existed; once dedup dropped the OCR lines AX already covered, its "on"
numbers came out far too low (comparison.md, Result 1e).

`swift test` runs 206 tests. `RedTeamTests` is the R1 red-team set: every attempt must be refused and audited. Positive controls guard against a daemon that simply refuses everything. On 2026-09-28 the suite was mutation-checked by removing the hit test, the chord filter, and the frontmost halt; each removal failed the tests that should catch it.

### Geometry suite

`bench/geometry/run_vm.sh` runs `bench/geometry/collect.py` in a throwaway `cu-base` clone per display config: `hidpi` (1440×900 pt @2x) and `1x`. Run `CU_BENCH=1 scripts/build-app.sh` (into `dist-bench/`) first; `swift build` alone does not update `dist-bench/`. The suite turns `debug_native_images` on, which only a bench build starts with. Filter with `ONLY="pos-center occlusion"` (scenario prefixes) and `CONFIGS=hidpi|1x`. Results (numbers only) and overlays of failing cases go to `bench/runs/geometry-<ts>/` (gitignored).

Ground truth never comes from the pipeline under test: marker positions come from the fixture's own layout, click landings from its `mousedown` events. Four paths are checked against it:

| path | what | pass |
|---|---|---|
| A | markers found in the native composite, mapped to global points | ≤ 2 pt |
| B | AX frames of the marker buttons | ≤ 2 pt |
| C | a real click at the A point, as the fixture saw it land | ≤ 2 pt |
| D | markers found in the downscaled (model) image, mapped back | ≤ 1 sent pixel |

Scenarios cover window positions and sizes, off-screen and oversized windows, frameless windows, two windows, sheets, context menus, occlusion by a non-granted app, an invisible (alpha 0) always-on-top window of another app that takes clicks, and its click-through twin as a positive control, minimized and hidden apps, stale snapshots, animation, full screen, and the menu bar and Dock (including autohide and left-docked). A click must either land on its marker or be refused; landing anywhere else fails. Scenarios can be marked `xfail` (a known gap with a planned fix): a failure is shown but tolerated, a pass fails the run so the marker gets removed. The runner exits non-zero unless every config produced results and everything passed; each config's full output is in `runner.log`.

Two results shaped the daemon:

- **Attached sheets are never captured on their own.** SCK renders a scaled copy of the whole parent into a sheet's single-window capture (39.6 pt off); the parent's capture already contains the sheet, correctly placed (0 pt). Sheet pixels come from the parent's capture; OCR text and AX elements on the sheet are attributed to the sheet window (`canary --sheet`, 2026-09-29).
- **The leak test.** A non-granted window shows a random `LEAKCANARY` string; the granted window shows `POSCTRL` as a positive control (pixels only, hidden from AX, so it exercises OCR). The canary must not appear in the daemon's OCR, in a `zoom` over both texts (its OCR and its image), in either composite or the zoom image re-read by OCR on the host, or in any file the daemon wrote. `LEAK_SELFTEST=1` puts the canary in the granted window, and the test must FAIL.
- **System overlays are expanded into their visible parts, not their apps' other windows.** The Dock's and Notification Center's full-display windows (layers 20 and 21) are replaced by their app's top-level AX frames; Notification Center's include its desktop widgets, which are separate desktop-level windows, so parts matching another window of the same process keep that window's place (2026-10-10: the widgets had been drawn above the fixture whenever a banner window was up).
