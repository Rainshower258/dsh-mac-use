# 在自己的 Mac 上使用 computer use（「电脑操作」模式）

cu-runtime 由两部分组成：

- **守护进程** `~/Applications/CURuntime.app`：截图、读取界面、执行点击和输入。所有安全决定都由它做出，授权弹窗也由它弹出。
- **dsh 插件包**：在日常使用的 dsh 里增加一个「电脑操作」模式（只有这个模式的会话能看到 cu_* 工具，而且看不到别的工具），并提供一个插件页，用来安装、启动和设置守护进程。

安装和管理只有一条路径：**dsh 的插件页**。`scripts/install.sh` 只做预检、清理失效的权限记录并给出引导，不替用户安装。技术细节见设计说明（`docs/DESIGN.zh-CN.md`）的「可安装的 dsh 插件包（电脑操作模式）」一节。

## 0. 怎么让它立刻停下

agent 正在操作、需要它马上停下时，**一步就够**：

```sh
pkill -x cu-runtime
```

或者打开"活动监视器"，搜索 `cu-runtime`，选中后点"强制退出"。

- **守护进程一停，所有动作立刻失效。** 插件没有自己操作屏幕的能力，模型手里什么都不剩。
  「电脑操作」模式开启了 `autoStart`：守护进程没在运行时，第一次 cu_* 调用会用 `open -g` 打开已安装的 app（只打开插件验证过的正式版，见 3.1）。但这只限于用户还没停过它：守护进程被有意停掉时（`pkill`、Ctrl-C、插件页的「停止」、设置窗口的停止按钮、`uninstall.sh`），它退出前自己在状态目录里留一个停止标记；之后不再自动打开，直到用户自己启动它（插件页「守护进程」标签上的「启动」，或 `open ~/Applications/CURuntime.app`），下一次连接会清掉标记。重启电脑后标记自动作废。**强制退出（或崩溃）来不及留标记**：只有当时有「电脑操作」会话正连着守护进程（最近一次 cu_* 调用在 5 分钟以内）时，插件才会替它留下；所以要确保它停着不再被打开，用 `pkill`，而不是强制退出。
- 正在弹出的授权窗口也会随之关闭（虚拟机实测：弹窗开着时发 SIGTERM，守护进程 10 秒内退出）。
- `pkill` 发的是 SIGTERM，守护进程退出前会还原它改过的系统状态（输入法、Electron 的 AX 开关）。强制退出不会还原，但下次启动时会根据记账文件补上。
- 停掉守护进程**不会**撤销系统权限，撤销方法见第 6 节。

## 1. 数据去向和存放位置

- **批准后，该应用窗口中的内容（截图、AX 文字、OCR 结果）会发送给会话所用模型的服务商**（例如云端的 DeepSeek）。沙箱隔离的是"执行"，不隔离"数据"。授权弹窗里也写着这一句。
- 只有已批准的应用的窗口会被截图和读取。其他窗口挡在它前面时，在截图里是一块灰色。
- **会话记录（含截图）和日常 dsh 的其他会话存放在一起**，都在 `~/.dsh` 里：「电脑操作」模式的会话就是日常 dsh 的会话，没有单独的目录。
- **dsh 的遥测和反馈上传由 dsh 自己的设置决定**，本插件不改动它们。反馈上传（`FEEDBACK_ONLY`）会发送用户提交反馈的那个会话，其中的截图也在内。
- 守护进程的审计日志默认在 `~/Library/Application Support/cu-runtime/audit/`，每天一个文件；存放位置和保留天数可在插件页或设置窗口的「日志」页更改（更改位置时已有文件随之迁移，写入所选文件夹下的 `cu-runtime-logs/`）。每次操作的放行与拒绝、授权、撤销、设置变更、设置窗口里的每次点击都记在里面，屏幕上的文字不会写进去。
- 插件页安装守护进程时的构建目录、签名证书的记录和操作日志在 `~/Library/Caches/cu-runtime/`。

## 2. 安装（只做一次）

守护进程只能**从源码构建**：在本机编译，并用本机生成的证书签名，没有现成的安装包。构建、签名和安装都由插件页完成。需要 macOS 14 或更新的版本。

下面的命令都在"终端"App 的窗口里执行（启动台或 Spotlight 里搜"终端"）。**不要通过 SSH 远程执行**，dsh 也要在本机的图形界面里运行：签名要用登录钥匙串，SSH 会话里钥匙串是锁着的，签名会报 `errSecInternalComponent`；插件页在 SSH 会话里会拒绝安装、签名和启动守护进程。

### 2.0 两种添加方式

- **用仓库链接（推荐）**：装好 2.1 的前置条件后，在插件页「添加插件」里直接填仓库链接 `https://github.com/Rainshower258/dsh-mac-use`（2.4）。dsh 用 pnpm 下载这个仓库；仓库里带着构建好的插件文件，不用自己构建，也用不到下面的 install.sh 和 2.2。
- **从源码（要改代码或调试时）**：获取源码（2.2），用下面的 install.sh 预检并构建，再在插件页按路径添加（2.4）。

从源码添加时，拿到源码（2.2）以后，在终端执行：

```sh
zsh ~/cu-runtime/scripts/install.sh
```

它依次做四件事：

1. **预检**：macOS 版本（14 或更新）、是否在 SSH 会话里、Xcode 命令行工具、Node.js 24、dsh 和它的版本、PATH 里有没有 `pnpm`（添加插件要用，没有时提示 `npm i -g pnpm`），以及日常的 `~/.dsh` 里有没有 API key（只检查有没有，不输出 key）。缺的一次全部列出来，并按该装的先后排好（2.1）。
2. **清理失效的权限记录**：已经装了 `~/Applications/CURuntime.app` 时，经 LaunchServices 运行它的自检；哪一项权限（辅助功能、屏幕录制）没有生效，就用 `tccutil reset` 清掉这个 bundle ID 在该项下的记录（与这个 app 不符的记录，清掉也不损失什么），并退出系统设置，然后说明清掉了哪几项，提示到插件页「守护进程」标签点「授予权限」重新申请。这一步本身不申请任何权限。还没装的话，它提示在插件页安装。
3. **安装插件依赖并构建**：在 `plugin/` 里执行 `npm ci`（`plugin/node_modules` 是链接时不动它），然后在仓库根目录执行 `npm run build`，这样 dsh 可以按路径添加这份源码。
4. **打印引导**：后面的步骤（2.4 到 2.6、第 3 节）按顺序列出，连同立刻停下的命令、设置窗口和卸载的命令。

它不签名、不构建 app、不弹钥匙串密码框，也不用 sudo；可以反复运行。**更新源码以后也要再运行一次**（或者手动执行 `npm run build`），然后重启 dsh（6.2）。

### 2.1 前置条件

1. **Xcode 命令行工具**（提供 Swift 编译器、git，构建守护进程要用）。在终端执行：

   ```sh
   xcode-select --install
   ```

   在弹出的窗口里点"安装"，等它装完。已经装过的话，会提示已安装，跳过即可。插件页上没有命令行工具时，也有一个「安装命令行工具」按钮，打开的是同一个安装窗口。

   **磁盘空间不够时：**这个安装窗口要求先空出**大约 25 GB** 可用空间，虽然工具本身只有 1 GB 左右；不够的话它会提示 "Can't install the software because there is not enough disk space"。这时改用下面四行，只下载工具本身：

   ```sh
   touch /tmp/.com.apple.dt.CommandLineTools.installondemand.in-progress
   softwareupdate --list | grep "Command Line Tools"
   sudo softwareupdate -i "Command Line Tools for Xcode 26.6-26.6"
   rm /tmp/.com.apple.dt.CommandLineTools.installondemand.in-progress
   ```

   第二行会列出可用的版本，把第三行引号里的名字换成列表中 `Label:` 后面、与本机 macOS 版本对应的那一个。第一行不能省：没有这个文件，列表里不会出现命令行工具，安装会报 "No such update"。

   装好后执行 `xcode-select -p`，应显示 `/Library/Developer/CommandLineTools`。

2. **Node.js 24**。到 <https://nodejs.org> 下载 macOS 安装包（`.pkg`，选 24 版本），双击，按提示装完。装好后执行 `node --version`，应显示 `v24.` 开头。

3. **dsh**。目前测试过、受支持的版本是 0.2.1-rc.2（2026-10-17 起；之前是 0.2.0-rc.2，再之前是 0.1.5-rc.3），请装这个版本（更新的版本还没验证）：

   0.1.x 不能用：0.2.x 起预设的写法变了，0.1.5 加载不了这里的配置。必须用 0.1.5-rc.3 的话，请用本仓库的 `9c6f36d` 提交。

   ```sh
   sudo npm install -g @deepseek-ai/dsh@0.2.1-rc.2
   sudo chown -R "$(id -u):$(id -g)" ~/.npm
   ```

   - `sudo` 会要求输入登录密码（输入时屏幕上不显示字符）。
   - **第二行不能省。**带 `sudo` 安装会让 npm 的缓存目录 `~/.npm` 归 root 所有，之后不带 `sudo` 的 `npm ci`（2.0 第 3 步、2.4）会报 `EACCES` 和 "Your cache folder contains root-owned files"。第二行把它还给当前用户。
   - 安装时 npm 可能提示 `install-scripts`，建议加上 `--allow-scripts=…`。**可以忽略**：被跳过的那些脚本，对这个版本的 dsh 没有影响（2026-10-10 核查过：node-pty 用的是预编译文件，且已经带可执行权限）。装好后执行 `dsh --version`，应显示 `0.2.1-rc.2`。
   - 也可以用 dsh 的桌面版（DeepSeek Harness.app）：在它的插件页按路径添加本插件、安装守护进程、用「电脑操作」模式完成任务，已在 2026-10-22 实测通过。

4. **pnpm**。dsh 的「添加插件」调用的是它 PATH 里的 `pnpm`；用 npm 安装的 dsh 不附带 pnpm，要先装上：

   ```sh
   npm i -g pnpm
   ```

   （如果 npm 的全局目录归 root 所有，这一行同样要加 `sudo`，之后再执行一次上面 `chown` 那行。）没装的话，添加插件只显示"退出码 127"，没有别的输出（dsh 的日志里是 `spawn pnpm ENOENT`）。桌面版自带 pnpm，不用另装。以后更新插件，是在插件页里先移除、再添加新版本的包，同样要用到 pnpm。

5. **API key**。日常的 dsh 第一次启动时会要求填写 API key（DeepSeek 的 key 在 <https://platform.deepseek.com> 创建）：

   ```sh
   cd ~
   dsh web
   ```

   浏览器会打开 dsh 网页，第一次打开会弹出 **"Add an API key to get started"**：把 key 填进 "API key" 一栏，点 **Save and continue**。（`dsh web` 会把当前目录当成默认工作区，所以先 `cd ~`，不要在源码目录里运行。）key 只存在日常的 `~/.dsh` 里，只有一份。

### 2.2 获取代码（只在从源码添加，或要用第 6、9 节的脚本时需要）

在终端执行：

```sh
git clone https://github.com/Rainshower258/dsh-mac-use.git ~/cu-runtime
```

也可以在仓库页面点 Code → Download ZIP。用 Safari 下载时，它一般会**自动解压**，并删掉 zip，"下载"文件夹里直接出现一个 `dsh-mac-use-main` 文件夹；没有自动解压的话，双击 zip 即可。把这个文件夹改名为 `cu-runtime`，放在哪里都可以。下文以放在个人文件夹为例，路径是 `~/cu-runtime`；放在别处（比如桌面，`~/Desktop/cu-runtime`）的话，把下文命令里的路径换掉。dsh 按路径加载这份源码，所以添加插件以后不要移动或删除它。

### 2.3 签名证书

插件页第一次安装守护进程时，如果登录钥匙串里还没有签名证书，会用 `scripts/make-signing-identity.sh` 自动生成一张自签名的代码签名证书 `cu-runtime-signing`，有效期 10 年，不会弹窗。也可以事先在终端里自己生成：

```sh
cd ~/cu-runtime
zsh scripts/make-signing-identity.sh
```

- **为什么需要：** macOS 把"辅助功能"和"屏幕录制"两项权限绑定在 app 的签名证书上，而不是某一次构建上。用同一张证书签名，以后重新构建也不用重新授权。
- **平时请不要删除这张证书。** 删掉以后，下一次构建在系统看来就是"另一个 app"，两项权限都要重新给。唯一的例外是有意轮换证书（6.2），那时删掉旧证书、重新授权一次正是目的。
- 证书没有设成"受信任"，也不需要：签名和权限都不受影响。所以 `security find-identity -v` 不会列出它；去掉 `-v` 就能看到，后面标着 `CSSMERR_TP_NOT_TRUSTED`，这是正常的。
- 已经有这张证书时，再运行一次只会提示 "already exists"，不会重复创建。
- 生成时它把证书本身（公开的部分，不含私钥）另存一份到 `~/.cu-runtime-signing/cert.pem`，以后核对钥匙串里的证书还是不是这一张（插件页会显示签名证书的 SHA-1）时可以用：`openssl x509 -noout -fingerprint -sha1 -in ~/.cu-runtime-signing/cert.pem`。重新列一遍钥匙串不能说明什么：那只是钥匙串现在的内容。
- **本机的 `cert.pem` 只是为了方便，不是可靠的参照。** 它是用户目录里的普通文件，本用户的任何进程都能改写它；脚本重新创建签名身份时，也会把已有的 `cert.pem` 改名为 `cert.pem.replaced-<时间>` 再写入新的。所以它旁边出现 `cert.pem.replaced-*`，就说明 `cert.pem` 被改写过，在插件页「确认当前证书」之前应先查明原因。同一用户的代码无法替换的参照，是保存在这台 Mac 之外的 `.p12` 备份（或同样保存在这台 Mac 之外的 `cert.pem`）：`/usr/bin/openssl pkcs12 -in <备份的 .p12> -nokeys -clcerts | /usr/bin/openssl x509 -noout -fingerprint -sha1` 以同样的格式读出其中证书的 SHA-1（要输入 `.p12` 的密码，不会写出私钥）；插件页显示证书变化时，应与它对照。
- 在它会另存证书之前生成的身份没有这个文件（再运行一次脚本会提示）：从这个身份的 `.p12` 备份里取出证书，`/usr/bin/openssl pkcs12 -in <备份的 .p12> -nokeys -clcerts -out ~/.cu-runtime-signing/cert.pem`（要输入 `.p12` 的密码，不会写出私钥；`/usr/bin/openssl` 是系统自带的 LibreSSL。PATH 里排在前面的 OpenSSL 3，例如 Homebrew 装的那个，不加 `-legacy` 读不了这种 `.p12` 里 RC2-40 加密的证书）。
- **每次签名都要输入登录密码（2026-10-20 起）。** 私钥的访问控制里不再信任 `codesign`，所以每次构建签名时，macOS 都会弹出"codesign 想要使用钥匙串中的密钥…进行签名"，要求输入登录钥匙串的密码。输入后点 **允许**，**不要点"始终允许"**：点了以后 `codesign` 会被加入访问控制，以后签名不再询问。这样做的目的：这台 Mac 上的任何程序都不能在用户不知情的情况下，用这张证书签出一个冒充 CURuntime、沿用两项权限的程序。
- **2026-10-20 之前生成的证书**仍信任 `codesign`，签名不会询问。改成需要确认（不换证书，两项权限保留）：打开"钥匙串访问"→ 左侧"登录"→ 搜索 `cu-runtime-signing` → 双击类型为"专用密钥"的那一项 →"访问控制"→ 在"总是允许这些应用程序访问"列表里选中 `codesign`，点"–"→"存储更改"（需要输入登录密码）。之后安装或更新一次守护进程，确认签名时弹出密码框即可。
- 证书的 `.p12` 备份（如果另外保存过）不要和它的密码一起放在这台 Mac 上：拿到这两样，就能把私钥导入别的钥匙串并重新信任 `codesign`，绕过上面的确认。

### 2.4 添加插件并安装守护进程

用仓库链接添加时，跳过第 1 步。从源码添加时，用了 2.0 的 install.sh 的话，第 1 步也已经做完；没用的话：

1. **构建插件**（第一次还要安装依赖）：

   ```sh
   cd ~/cu-runtime
   (cd plugin && npm ci)
   npm run build
   ```

   报 `EACCES` 的话，是 2.1 第 3 步的第二行没执行，补上再来。

   > 注：`plugin/node_modules` 如果是用 `plugin/scripts/link-deps.sh` 链到上游参考仓库的（开发用的机器上是这样），**不要**运行 `npm ci` 或 `npm install`，否则 npm 会顺着链接写进上游目录。

2. **启动日常的 dsh**：`dsh --profile web`，或者打开 dsh 的桌面版。
3. **添加插件**：在 dsh 的插件页点「添加插件」，填入仓库链接 `https://github.com/Rainshower258/dsh-mac-use`；从源码添加时，填这份源码的**完整绝对路径**（例如 `/Users/<用户名>/cu-runtime`；dsh 不认 `~/` 开头的路径；install.sh 的引导会打印出完整路径），添加后点「启用」。
4. **安装守护进程**：打开这个插件的详情页，在「守护进程」标签点「安装守护进程」。它把源码复制到 `~/Library/Caches/cu-runtime/build` 里构建（第一次要编译几分钟），用 `cu-runtime-signing` 签名（没有就先生成，2.3），确认新 app 是正式版本（不是 bench 构建）并且签名符合要求，然后替换 `~/Applications/CURuntime.app`、启动它并做一次自检。签名时会弹出钥匙串窗口，要求输入登录密码：输入后点 **允许**，不要点"始终允许"（原因见 2.3）。密码框被取消或拒绝、或者屏幕已锁定时，安装失败，已装的 app 保持原样，重新点一次即可。

### 2.5 授予两项权限

在「守护进程」标签点「授予权限」。每点一次只打开系统设置里的一个面板：

1. 先打开"辅助功能"：在里面打开 **CURuntime** 的开关，然后点「检查权限」；
2. 辅助功能显示为已授予以后，再点一次「授予权限」，打开"屏幕录制"（"屏幕与系统录音"），同样打开开关，再点「检查权限」。

插件页从不清除已有的授权记录。两项权限里有一项开关已经打开、却始终显示未授予（通常是旧证书签名时留下的记录），按第 6.1 节处理。

### 2.6 模式检查

「守护进程」标签的「模式检查」显示 **正常**，安装就完成了。它检查的内容见第 7 节。显示有问题时，按它列出的每一行处理，再点「重新检查」。

## 3. 每次使用

1. **启动 dsh**：日常的 `dsh --profile web`，或 dsh 的桌面版。守护进程不会开机自启，也没有装 LaunchAgent；平时不用先手动启动它：第一次 cu_* 调用会自动打开它（3.1）。**用 `pkill` 或插件页的「停止」停过以后不会自动打开**，直到下次重启 Mac（强制退出的情况见第 0 节）；这时在插件页「守护进程」标签点「启动」，或者执行 `open ~/Applications/CURuntime.app`。
2. **新开一个会话，选「电脑操作」模式**，并在会话里选一个**支持图片输入的模型**。插件不固定模型和推理强度，由用户自己选；不支持图片的模型看不到截图。
3. 在对话里提需求，例如："打开 QQ 置顶会话，读最新三条消息"。**使用时让 dsh 的网页（或桌面版窗口）一直在前台**（理由见第 4 节"弹窗关闭以后"）。需要确认时，dsh 会弹出审批（输入法切换，第 4 节），守护进程会弹出它自己的授权窗口（第 4 节）。
4. 用完以后可以让守护进程继续运行；要退出就执行 `pkill -x cu-runtime`，需要它立刻停下时也是这一条（第 0 节）。退出以后再用，按第 1 步手动启动。

**语言。**模型回答用的语言、授权窗口和输入法审批里的文字，都跟着 **dsh 的界面语言**走（目前只有中文和英文）：

- dsh 的界面语言在日常 dsh 的设置里改。**模型的回答语言从新开的对话开始生效**：同一个对话里，系统提示词在对话开始时就定下了，改了也不变（2026-10-10 实测）。
- dsh 没设语言时，跟系统语言走（系统设置 → 通用 → 语言与地区，排在第一的那个）。
- 想让模型临时换一种语言回答，直接在对话里说"用英文回答"之类，它会一直用那种语言，直到再次改口。**用另一种语言打字不算**：输入法没切换、顺手打了英文，它照样用 dsh 的语言回答（2026-10-10 起）。

**每轮结束后焦点会自动回到 dsh。**模型操作 QQ 时会把 QQ 切到前台。如果一轮结束后焦点还停在 QQ，接着打的字会进 QQ 的输入框，按回车就发给了联系人。所以每轮结束时（不管是正常做完、用户按了停止，还是出错），守护进程会把焦点还给这一轮开始时在前台的应用，也就是用户打字的那个浏览器。

- **回到 dsh 后，先点一下输入框再打字。**浏览器回到前台时，光标暂时不会自动回到 dsh 的输入框（2026-10-08 实测）。这时打的字不会进 QQ，也不会触发 dsh 网页上的任何操作：dsh 网页没有单键快捷键，审批按钮也不会自动获得焦点。只是这些字没有进输入框。
- 如果这一轮中途用户自己切到了别的应用，它不会把焦点拉回来：只有当前在前台的是这一轮模型操作过的应用时，才会归还焦点。
- **一轮还在进行时，焦点是在 QQ 的**：这时不要打字，字会进 QQ。要彻底解决，得等以后"检测到用户本人在操作就自动暂停"这个功能。
- 想让它停在 QQ（比如让它打开某个会话，然后用户自己接着操作）：在插件页或设置窗口的「行为与模型」页关掉「每轮结束后归还焦点」。
- 审计里的 `access.turn_end` 行会记录结果：`focus` 为 restored（已归还）、skipped（没归还，`focus_skipped` 写原因）或 failed（归还失败）。

**第一次看 QQ 会慢几秒。**守护进程第一次读 QQ 时，要先打开 QQ 的 AX 开关，再等 QQ 把界面结构交出来。宿主机上 QQ 要 2 到 5 秒，所以守护进程最多等 5 秒。超时的话，模型手里只有截图和 OCR，可能读错，比如把一个大表情当成最后一条消息（2026-10-09 实测）。这时插件会在观察结果里提示模型再看一次。QQ 被最小化、隐藏或者没有窗口时，守护进程不等，直接告诉模型应用处于哪种状态，模型用 `cu_launch` 把窗口叫回来（只需要浏览档）以后才会去等。审计里 `ax.manual_accessibility` 行的 `settle.reason` 是 `grew_and_settled`，说明等到了；是 `unchanged` 或 `timeout`，说明没等到。

### 3.1 自动启动（autoStart）

「电脑操作」模式开启了 `autoStart`：守护进程没在运行时，第一次 cu_* 调用会经 LaunchServices（`open -g`，不抢焦点）打开已安装的 `~/Applications/CURuntime.app`。打开之前，插件按插件页启动守护进程时的同一套规则核对这个 app：已安装；钥匙串里只有一张名为 `cu-runtime-signing` 的证书；是正式版本（不是 bench 构建）、符合这张证书的签名要求，并带 hardened runtime。核对只做只读的查询（`plutil`、`security find-identity`、`codesign --verify`、`codesign -d`），约 1 到 2 秒。

不符合的 app 不会被打开：d4faaeb（2026-10-20）之前的构建、bench 构建、没有 hardened runtime 的构建、钥匙串里有多张同名证书的情况都在内。这时模型收到的报错是：

```
cu-runtime daemon is not reachable (the installed CURuntime.app is not a release build the plugin verified: <code>). The daemon is not started. Do not start it yourself: tell the user, who can install or update CURuntime.app on the plugin page's 守护进程 tab.
```

`<code>` 是原因：`not_installed`（没有安装）、`identity_missing`（钥匙串里没有签名证书）、`identity_ambiguous`（有多张同名证书）、`not_release_build`（不是正式版本）、`signature_mismatch`（签名与本机的证书不符），`internal` 表示核对本身出错。**解决办法**：到插件页「守护进程」标签，按页面的提示安装、更新或重新安装守护进程（多张同名证书时，先在"钥匙串访问"里只保留授予过权限的那一张）。被拒以后的 30 秒里，再次调用直接返回同一个报错，不再重复核对。

用户停过的守护进程不会被自动打开（第 0 节）。

## 4. 授权弹窗

模型第一次接触一个**还没批准**的应用（观察也算接触，不只是点击或输入），那次调用什么都不做，守护进程先弹出 macOS 原生对话框；用户批准了，这次调用才继续。一个应用**只问一次**，问的是可操作档（看、点、输入、打开都在内），和官方 cua-macos 的做法一样（2026-10-16 起；之前是先拒绝、模型带档位和理由重发一次才弹窗，每个应用要多走一轮，还常常浏览档、可操作档各弹一次）。模型可以在那次调用上附一句理由，会显示在弹窗里。

- 拒绝过的应用，**这一轮里**不再弹窗。用户发下一条消息以后，模型碰到它会再问一次。所以误点了"拒绝"，在下一条消息里让它再试就行，不用新开对话。
- dsh 会话的审批策略是 `never` 时，一律不弹窗。
- **运行 dsh 的那个浏览器永远批不了**：每轮开始时在前台的应用（用户打字的那个浏览器）在整个会话里都不能申请、不能看、不能操作，直接拒绝（`dsh_host_app`），也不弹窗。否则模型批到它以后，可以自己去点 dsh 网页里的"允许一次"。要让模型操作浏览器，得换一个不运行 dsh 的浏览器。

**弹窗关闭以后**，焦点会回到弹窗前在前台的那个应用，模型接下来的动作才能继续：守护进程自己在硬拒绝清单里，它留在前台的话，所有动作都会停下。所以**使用时让 dsh 网页保持在前台**。如果弹窗前在前台的是终端（比如正在终端里用 Claude Code），焦点会回到终端；终端也在硬拒绝清单里，接下来的动作会被"硬拒绝应用在前台"拒绝。这是安全方向的行为，不是故障：切回 dsh 网页，让模型再试一次就行。

弹窗里显示的内容：
- **系统解析出来的应用**：图标、名称、bundle ID、安装位置。这是守护进程实际找到的那个应用，不是模型给的字符串。
- 申请的档位。
- "窗口内容会发送给模型服务商"这句提示。
- 模型给出的理由。理由标着"不可信"，因为模型可能被屏幕上的文字操纵过。
- **申请者**：发起申请的进程名和 PID，平时是运行 dsh 的 `node`。自从守护进程启动以来，如果还没给这个进程批准过任何东西，下面会多一句"这是这个进程第一次申请"。**刚才没让 dsh 操作屏幕，却弹出了窗口，就点拒绝。** 只有在申请者自己标记过的那一轮对话里，守护进程才会弹窗；不过别的程序（比如 bash 用 `open` 打开的程序）可以用自己的任务名来申请（第 8 节），这一行就是用来分辨申请者的。

| 按钮 | 含义 |
|---|---|
| **拒绝**（默认按钮，按回车就是它） | 这一轮里不再为这个应用弹窗；用户发下一条消息后可以再问 |
| **仅本轮** | 到这一轮对话结束为止 |
| **本次会话** | 整个 dsh 会话有效，从批准时起最长 30 分钟 |
| **始终允许** | 记进持久名单（第 5 节）。应用必须是签过名的；可操作档选它要先过 Touch ID 或密码（2026-10-16 起） |

两次批准叠在一起时，各管各的：比如先给 QQ 批了"浏览·本次会话"，后来为了按回车又批了"可操作·仅本轮"。这一轮里 QQ 是可操作档；这一轮结束后，QQ **退回浏览档**，原来那份"本次会话"还有效，不会再弹窗问浏览档。

**输入法**：当前输入法是拼音这类输入法时，模型要输入字母或标点，得先把输入法临时切到英文键盘（ABC），输完立刻切回。切之前 dsh 网页里会弹出审批，用中文写明是哪个输入法、往哪个应用里输入，点"允许一次"就行。只输入数字、空格、换行，而且拼音里没有正在组的字时，不用切换，也不弹审批。

模型想看一个**没在运行**的应用时，插件不弹窗（批了也没东西可看），让模型直接用 `cu_launch` 打开，那一次弹窗把打开和使用一起批了。

**档位**（2026-10-16 起插件只申请可操作档；浏览档还在，用于以前"始终允许"进持久名单的应用，和终端里 `cu-runtime grants add` 加的条目）：

- **浏览**（内部标识 `read`）：查看窗口、左键单击一次、滚动、按下按钮（AXPress）、把窗口提到前面（AXRaise），以及用 `cu_launch` 把**已经在运行**的应用叫到前面（没有窗口就重开一个，和点 Dock 图标一样）。**左键单击和按下按钮能按到任何按钮，包括"发送"**；不能输入文字、按键、设值，也不能拖拽。
- **可操作**（内部标识 `full`）：在浏览之外，还能输入、按键（白名单里有 ⌘Q 退出、⌘W 关窗口）、设值、拖拽，以及**启动没在运行的这个应用**（`cu_launch`）。只能打开弹窗里批准的那一个应用，硬拒绝清单照样生效。是否在运行由守护进程在执行那一刻检查，应用刚好退出了，浏览档就不能把它启动起来。

**菜单栏**（`cu_menu`，只在可操作档能用）：模型可以通过辅助功能使用应用自己的菜单栏，比如"格式 → 字体 → 粗体"，不截图。苹果菜单（关机、重启、睡眠、注销都在里面）和"服务"子菜单永远拿不到。菜单标题不写进审计。窗口里有对应控件时，模型会优先用控件。

应用没在运行时，弹窗里会多一行"它现在没在运行。批准后模型可以打开它"。已批准的应用如果没在运行或者没有窗口，模型看屏幕时插件会直接告诉它，让它用 `cu_launch` 打开或者请用户打开，不要对着猜出来的坐标点（2026-10-09 计算器实测：没提示时模型编了坐标，还去申请了没用的权限）。

不管哪一档，下面这些安全底线都**照常生效**：
- 硬拒绝清单（终端、钥匙串、系统设置、守护进程自己，等等）；
- 系统快捷键白名单（锁屏、注销、⌘Tab 之类永远拒绝）；
- 密码框里禁止输入；
- 点击前的命中测试、前台校验、过期元素检测。

**防止弹窗轰炸**：
- 硬拒绝清单和用户黑名单里的应用根本不弹窗，直接拒绝；
- 拒绝过的应用，这一轮里不再弹窗。下一轮要等用户发了新消息，模型伪造不了这一步，所以就算它被屏幕上的文字操纵，也只能做到用户每发一条消息、它最多再问一次；
- 每轮对话最多弹 3 次（同一个应用从浏览档加到可操作档的那次不计）；
- 弹窗里有实时倒计时，120 秒没有回答就当作拒绝。超时不算"拒绝过"，下一轮还可以再问。

**授权到期或被撤销以后**（"本次会话"最长 30 分钟，或者用 `grants revoke`、插件页「概览」撤销了），模型在同一个会话里再用这个应用，会和第一次一样弹窗再问一次。不用新开会话。

**一个已知限制**：dsh 没有"会话结束"的通知。"本次会话"的授权会一直留在守护进程里，直到 30 分钟到期，而且只归申请它的那个 dsh 进程使用（设计说明的「连接认证」一节）。要让授权立即作废，在「概览」里撤销，或者退出守护进程。

### 4.1 让应用打开文件时，macOS 自己的询问

模型可以让已批准（可操作档）的应用直接打开一个文件或网址（`cu_launch` 的 `open`，比如把一个 txt 用文本编辑打开，图片用预览打开）。守护进程把文件交给应用之前，macOS 会要求**守护进程自己**有权读这个文件。所以第一次打开桌面、文稿、下载等受保护文件夹里的文件时，macOS 会弹出它自己的询问："CURuntime 想访问桌面文件夹"。这是系统弹的，不是守护进程的授权窗口。

- **点"不允许"就行**（推荐）：守护进程自己并不需要读这个文件夹，它只是把文件交给应用，由应用去打开。虚拟机实测（2026-10-15）：点了不允许以后，这个文件夹里的文件照样能打开，而且不会再问。守护进程留在它本来的权限上（辅助功能、屏幕录制），不多拿一项。
- 点"允许"也可以：同样不再问，区别只是守护进程从此可以读这个文件夹（它不会主动去读；它只打开模型指定、并且它自己检查过的文件：只开普通文件，不开可执行文件、安装包、`.command`、`.webloc` 这类一打开就会运行或跳转的东西，也不开它自己目录下的文件）。想撤回：系统设置 > 隐私与安全性 > 文件和文件夹 > CURuntime。
- 这个询问弹出时，打开操作会一直等待回答。10 秒没回答，模型会收到 `open_waiting`，提示它请用户去回答系统的询问；回答以后（不管选哪个）文件会自己打开，模型不用再发一次。
- `/tmp` 里的文件不会弹询问（cu-std 的工作区 `~/.dsh-cu-std/work` 也不会，第 10 节）。

### 4.2 设置：插件页的标签和设置窗口

守护进程的设置有两个入口，内容相同：

- **插件页**：插件详情页上方的一排标签。「守护进程」是安装、启动、停止、授予权限、检查权限和模式检查；后面依次是守护进程的设置：「概览」「档位与默认」「应用名单」「快捷键」「隐私与审计」「行为与模型」「日志」。插件页上的每一项改动都经守护进程核对；放宽设置的改动要先在这台 Mac 上通过 Touch ID 或登录密码验证，等待验证时页面上方会显示这项改动和「取消」。
- **设置窗口**：守护进程自带的原生窗口，页面和插件页的设置标签相同。守护进程在硬拒绝清单里，所以模型看不到也点不到它。打开：

  ```
  ~/Applications/CURuntime.app/Contents/MacOS/cu-runtime settings
  ```

  守护进程在运行就直接弹出窗口；没在运行就带着窗口启动它。关掉窗口不影响守护进程。

各页的内容（以设置窗口为例）：

- **外观跟着 dsh 走**：dsh 设置里选的浅色/深色/跟随系统（`ui-theme` 的 `preference`：dsh 0.2.0 及以前在 `settings.yaml` 里，0.2.x 在各 profile 的 `cordis.patch.yml` 里），窗口每次打开时读一遍；几个 dsh 目录都设了的话，以最近改过的那份为准。配色用的是 dsh 自己的。语言跟审批窗口一样。
- **概览**：守护进程版本和运行时长、两项系统权限、正在生效的授权（每条可以单独撤销，也可以全部撤销）、最近拦截（读当天和昨天的审计，只有动作和原因；正常升权流程里的"先拒绝再申请"不列）。
- **应用名单**：
  - 始终允许：持久名单，可以移除（收紧，不用验证）。添加在弹窗里（可操作档要 Touch ID）、终端里或这一页上。
  - **用户黑名单**：模型看不到、碰不到、也不会弹窗的应用，任何档位都一样（拒绝原因 `user_denied`）。加入**立即生效**：正在生效的授权里有它就当场剔除，持久名单里有它也一并删掉。移出等于放宽，要 Touch ID / Apple Watch / 密码确认。可以从正在运行的应用里选、选 .app 文件，或手填 bundle ID，可以加备注。
  - 系统底线：编译进守护进程的硬拒绝清单，只读。
- **停止并撤销全部授权**：撤销所有授权，然后守护进程退出；退出前它留下停止标记（第 0 节），dsh 的插件不会自动再打开它；要再使用，先在插件页点「启动」或执行 `open ~/Applications/CURuntime.app`。
- 设置存在 `~/Library/Application Support/cu-runtime/settings.json`（0600），设置窗口在守护进程里直接改它；插件页经 socket 的 `settings.*` 方法也能改，但只能一次改一项：收紧立即生效，**放宽（移出黑名单、加入始终允许、打开某类发送等）一律先由守护进程自己弹 Touch ID / 密码验证**，客户端说"已验证"不算；目录和文件只经守护进程自己的选择框，路径不经 socket。模型用的 cu_* 工具里没有这些方法。手工改文件要重启守护进程才生效。每次改动都记审计（`settings.*`）。

## 5. 持久名单（"始终允许"）

名单文件是 `~/Library/Application Support/cu-runtime/grants.json`，权限 0600。名单按 **bundle ID + 应用签名** 记录：同一个 bundle ID 换成了别人签名的版本，旧授权自动作废，并写进审计（`access.persistent_invalidated`）。名单也可以在插件页或设置窗口的「应用名单」页查看和修改。

命令（建议加一个别名：`alias cu-runtime=~/Applications/CURuntime.app/Contents/MacOS/cu-runtime`）：

```sh
cu-runtime grants list                      # 查看名单
cu-runtime grants revoke QQ                 # 按名称或 bundle ID 撤销
cu-runtime grants add --full com.tencent.qq # 永久可操作档：执行这条命令时就记下应用当前的签名
```

- 永久的 **full** 是故意多设的一步：一个永久的 full，意味着以后任何一次会话里，模型都能直接往这个应用里打字、发消息，而不会再询问用户。
- 名单上的撤销对之后的申请立即生效。已经授给某次会话的那一份，最多保留到它的 30 分钟上限；想立刻作废，在「概览」里撤销，或者退出守护进程。

## 6. 系统权限

两种做法：

- **长期保留，需要时启动**：权限一直留着，守护进程只在被打开时才运行（插件的自动启动、插件页的「启动」或 `open`），不会开机自启。方便。
- **每次用完撤销**：用完后执行

  ```sh
  tccutil reset Accessibility dev.cu-runtime.daemon
  tccutil reset ScreenCapture dev.cu-runtime.daemon
  ```

  下次使用前重新做 2.5。这样更干净。

### 6.1 权限排查：开关打开了却不生效

（本节和 6.2、第 9 节用到的脚本在源码里。用仓库链接添加的，先按 2.2 取一份源码。）

系统设置里每项权限给 `dev.cu-runtime.daemon` 只留一条记录，记录里写着当初获得授权的那个 app 的签名要求。证书换过（6.2）或者装过别的证书签的构建以后，旧记录还在列表里、开关也开着，却和现在的 app 对不上，于是插件页一直显示"未授予"。插件页的「授予权限」不会清除已有的记录。处理办法：

```sh
zsh ~/cu-runtime/scripts/install.sh --permissions-only
```

它只做权限这一步：对已安装的 app 做一次自检，只把**没有生效**的那几项记录清掉（已经生效的不动），并退出系统设置（开着的系统设置可能把旧记录写回去）。它不做预检、不构建，所以用 dsh 桌面版或其他 dsh 版本时也能用。然后回到插件页，按 2.5 点「授予权限」重新授予。

不用脚本也可以手动处理：先退出系统设置，再执行

```sh
tccutil reset Accessibility dev.cu-runtime.daemon
tccutil reset ScreenCapture dev.cu-runtime.daemon
```

（app 必须还在 `~/Applications` 里，否则系统找不到它，命令会失败），然后按 2.5 重新授予。

### 6.2 更新源码以后：更新守护进程、清理旧构建

- **用仓库链接添加的**，要更新时在插件页移除插件，再用同一个链接添加一次，就会装上仓库当前的版本。**然后先重启 dsh**（`dsh web` 退出再启动，或退出再打开桌面版），再看「守护进程」标签，按下一条更新守护进程：不重启的话，dsh 里可能还留着替换前的插件，「更新守护进程」会用旧插件的源码构建（2026-10-23 在本机遇到过：构建的版本号是旧源码的，不是新包的提交号）。
- **从源码添加的，更新源码后**，先运行一次 `zsh ~/cu-runtime/scripts/install.sh`（或者在仓库根目录执行 `npm run build`），再重启 dsh：dsh 按路径加载的是源码目录里构建好的文件，不重新构建就仍在运行上一次的构建。然后看插件页「守护进程」标签：已装的 `~/Applications/CURuntime.app` 不是这份源码的正式构建（源码哈希不同、没有 hardened runtime，或者是 2026-10-20 之前装的）时，页面会提示更新，点「更新守护进程」（或「重新安装守护进程」）即可，签名时钥匙串要一次登录密码。
- **旧构建要清理。** 两项权限认的是签名证书，而不是某一次构建：用正式证书 `cu-runtime-signing` 签过的 CURuntime.app，放在哪里都带着这两项权限，LaunchServices 从归档或旧目录里一样能启动它（自动启动只打开验证过的 `~/Applications/CURuntime.app`，但别的程序仍可以用 `open` 启动这些副本）。能留下的只有 hardened 正式构建（`CUBench` 为 false、带 hardened runtime：3ecf445 起的 `build-app.sh` 才这样构建）；3ecf445 之前的构建都没有 hardened runtime，d4faaeb（2026-10-20）之前的还认 `--state-dir` 和测试用的开关。列出这台 Mac 上所有的 CURuntime.app：

  ```sh
  zsh ~/cu-runtime/scripts/find-release-builds.sh
  ```

  每个 app 列出路径、版本（CFBundleVersion）、`CUBench`、hardened runtime、签名证书和它的 SHA-1，并给出结论：keep（留下）、REMOVE（要删）、bench（bench 证书签的，只列出）、other（未签名、ad-hoc 签名或别的证书，只列出）。它用 Spotlight 查找，Spotlight 不索引的地方（这份源码和它的 `.claude/worktrees`、Spotlight 找到过构建的其他源码目录的 `.claude/worktrees`、`~/Library/Caches/cu-runtime`、`~/Applications` 里安装时用的临时名、`~/Archives`、临时目录）另用 find 查；命令后面还可以加上要一并查找的目录，例如移动硬盘。整个过程只读，不会弹出密码框。

  加上 `--delete`：先照样列出，然后在终端里输入 `yes` 才删除标为 REMOVE 的那些（直接删除，不进废纸篓，进了废纸篓的照样能启动）。有进程正在从其中某个 app 运行时，它不删，先要退出那个进程。删到 `~/Applications/CURuntime.app` 时它会提示：在下一次安装之前没有守护进程可用。废纸篓、Time Machine 备份和它看不到的磁盘里的副本找不到，所以这种做法永远不算彻底。
- **彻底的做法是轮换正式证书**：用新证书签的构建授权一次以后，系统里这个 bundle ID 的权限记录就改认新证书，旧证书签的构建不论放在哪里都失效。代价是两项权限要重新授予一次（这是 2.3 节"请不要删除这张证书"的例外：有意换证书）。步骤见设计说明的「签名」一节（旧构建）。

## 7. 模式检查

插件页「守护进程」标签的「模式检查」检查**正在运行的这个 dsh 的主目录**（`DSH_HOME`，默认 `~/.dsh`）里的每一个 profile：对每个 profile 运行一次 `dsh --profile <名称> --dump-config`，读合成后的配置（dsh 桌面版管理的 profile 无法从命令行合成，改为检查它自己的文件）。其他 dsh 主目录不在检查范围内。它要求：

- cu_* 工具只出现在本插件包的「电脑操作」模式里，而且只有一行；
- 这个模式开启了 `onlyCuTools`、以对话框确认应用（`appApproval: dialog`），没有关闭 `exclusive`；
- 任何 profile 都不加载别的电脑操作插件（包括上游的 dsh-computer-use）。

每个 profile 的结果是「正常」、问题（逐行列出）或「未检查」（例如找不到 dsh、某个 profile 的检查本身出错）。还装着插件页出现之前的旧版插件包的 profile 会被列为问题，并写明更新办法：先移除旧包，再在 dsh 插件页添加这个版本的包。

结果缓存 60 秒，点「重新检查」立即重跑。dsh 加载插件约 10 秒后也会自动检查一次，每一行问题、每个没能检查的 profile 都作为警告写进 dsh 的日志，以 `cu-runtime: mode check: profile <名称>:` 开头（没能检查的写 `not checked: <原因>`，例如找不到 dsh、dump-config 输出超过 8 MiB）；一个 profile 都没找到时写 `cu-runtime: mode check: not checked: no profiles under the dsh home`，页面显示「未检查」而不是「正常」；整个检查都无法运行时，日志里是 `cu-runtime: the mode check could not run: …`。`DSH_HOME` 为空或只有空白时按未设置处理（即 `~/.dsh`），和 dsh 自己一致。

## 8. 安全设计一览

- **cu_* 工具只在「电脑操作」模式里注册**，这个模式的 agent 拿不到 bash、文件、网页和子代理工具：dsh 给每个模式的其他工具，插件在 agent 第一步之前逐个拒绝（`onlyCuTools`）。日常 dsh 的其他模式看不到 cu_* 工具。模式检查（第 7 节）核对配置确实如此。
- **第二道保险在插件里**：模型只要能看到任何一个非 `cu_*` 的工具（bash、文件、run_code……），所有 `cu_*` 工具就拒绝执行，并说明是哪些工具（`exclusive`）。
- **授权弹窗由守护进程自己弹**，模型既看不到也点不到。守护进程的 bundle ID（`dev.cu-runtime.daemon`）在硬拒绝清单里，对它的观察和点击一律拒绝。
- 第 4 节里说的安全底线，在两种档位下都生效。

### 8.1 令牌（token）与 dsh 的沙箱

守护进程每次启动都在状态目录（`~/Library/Application Support/cu-runtime/`）里重新生成 `token` 文件（0600），连接 socket 的程序要先出示它。**dsh 的沙箱只限制写入，不限制读取**，所以在日常 dsh 的任何模式里，dsh 沙箱中的 bash 命令和 dsh 自己的文件工具都能读到这个 token。「电脑操作」模式里模型没有这些工具，但同一个 dsh 的其他模式（例如标准模式）有。这一点有意不靠改沙箱来解决，而是在这里写明。

拿到 token 的程序能做的：

- 读取设置快照（不含 token、状态目录路径和审计细节）；
- 做收紧方向的设置改动（立即生效）；
- 通过守护进程的弹窗申请某个应用：弹窗写明申请者的进程名和 PID，这个进程此前没被批准过时还会写明是第一次申请（第 4 节）；只有用户点了批准才算数；
- 为放宽方向的改动发起所有者验证（Touch ID 或登录密码）：必须由 Mac 前的人通过；一次验证被拒绝或取消以后，10 秒内不能再发起。

它做不到的：放宽任何设置；不经 Mac 前的人批准就让某个应用可用（没有弹窗的授权在正式版里关闭）；使用别的进程获得的批准（批准绑定在申请它的进程上）。

不在这层保护之内的情况：

- dsh 的 `danger-full-access` 模式：bash 不受沙箱限制地运行，守护进程和 bash 之间只剩守护进程自己的检查。切换到这个模式是用户自己的决定和风险。
- 经 `open`（LaunchServices）启动的程序：它在沙箱之外运行，可以读 token，用自己的任务申请应用（不能借用正在进行的对话，也不能在两轮之间申请）。弹窗会写明申请者，见第 4 节"申请者"。
- dsh 自己的进程：在 dsh 进程里运行的代码（别的插件，以及逃出 workflow 脚本隔离的代码）和本插件是同一个进程，可以使用插件已经获得的批准。
- 此外，bash 不经 cu 也能操作图形界面（osascript、screencapture、CGEvent），能做到哪一步取决于运行 dsh 的那个终端或应用的系统权限：不要给它"辅助功能""屏幕录制"或"自动化"权限。

## 9. 卸载

1. **先移除插件**：在 dsh 的插件页移除 cu-runtime。`uninstall.sh` 不碰 dsh 的任何 profile。
2. **再运行卸载脚本**：

   ```sh
   zsh ~/cu-runtime/scripts/uninstall.sh
   ```

   默认：停止守护进程，删除 `~/Applications/CURuntime.app`，退出系统设置并撤销"辅助功能"和"屏幕录制"两项权限。其余的默认保留，需要时加选项：

   - `--all`：同时删除守护进程的状态目录 `~/Library/Application Support/cu-runtime`（审计日志、"始终允许"名单、设置）；在设置里选过别的日志文件夹的话，那里的 `cu-runtime-logs` 不删，脚本会说明；
   - `--legacy-home`：同时删除已退役的旧目录 `~/.dsh-cu-desktop`（旧版本的独立 dsh 目录，含当时的会话、截图和 API key 副本）；
   - `--remove-cert`：同时删除签名证书 `cu-runtime-signing`（以后再安装时，两项权限要重新授予）；找不到证书时会说明，删除失败（例如通过 SSH 运行、钥匙串锁着）会报错并以退出码 1 结束；
   - `--yes`：删除前不再询问。

   日常的 `~/.dsh`（包括「电脑操作」模式的会话）、dsh、Node.js、命令行工具和源码都不动。另外这些也会留下，需要时手动删除：插件页的构建目录和操作日志 `~/Library/Caches/cu-runtime`，证书的公开副本 `~/.cu-runtime-signing/cert.pem`。

   撤销权限要在删除 app 之前做（系统靠 bundle ID 找到 app），脚本按这个顺序执行；app 已经不在时它不再尝试撤销，而是说明残留的记录（如果有）要到「系统设置 → 隐私与安全性」里选中 CURuntime 后点"−"删掉。

## 10. 实验：cu-std

cu-std 是一个实验性的 profile：dsh 的标准模式加一个只有 cu_* 工具的 `screen` 子代理，主代理照常有 bash。它**默认只装在虚拟机里**：`zsh scripts/install-cu-std.sh` 在真机上会拒绝安装，要加 `--real-mac` 才装（在真机上 bash 以当前用户的身份运行在守护进程旁边，见设计说明的「威胁模型」）。

- 需要 dsh 0.2.1-rc.2 或更新的 0.2.x：子代理的人设和工具改由 agent preset 配置，0.2.0 没有这项功能，`install-cu-std.sh` 会在写入任何文件之前拒绝。必须在 0.2.0-rc.2 上使用 cu-std 的话，请用本仓库的 `fcba171` 提交。
- 它有**自己的 dsh 目录** `~/.dsh-cu-std`（工作区是 `~/.dsh-cu-std/work`），安装时从日常的 `~/.dsh` 复制一份 API key 和界面语言；以后轮换 key 时，这份副本要单独更新。
- 它的 bash 命令经 `scripts/cu-sandbox-runner` 受限运行，读不到状态目录、连不上 socket；离开沙箱的调用由 dsh 自己的提权询问确认；workflow 关闭。

## 11. 排查

| 现象 | 原因 |
|---|---|
| cu_* 报错 "refuses to work while the model also has other tools (…)" | 当前模式给了模型别的工具。新开会话并选「电脑操作」模式；仍然报错时看「模式检查」（第 7 节） |
| cu_* 报错 "the installed CURuntime.app is not a release build the plugin verified: …" | 自动启动拒绝打开已装的 app（3.1）。在插件页「守护进程」标签安装、更新或重新安装守护进程 |
| 报错说连不上守护进程，并说它被停过（"It was stopped …"） | 用户停过守护进程，不会自动再打开（第 0 节）：在插件页点「启动」或执行 `open ~/Applications/CURuntime.app` |
| 插件页「模式检查」有问题 | 按列出的每一行处理（第 7 节），再点「重新检查」 |
| 「添加插件」只显示"退出码 127" | dsh 的 PATH 里没有 pnpm：`npm i -g pnpm`（2.1 第 4 步） |
| 审计里有 `approval_unavailable` 的拒绝 | 带 `"silent": true` 的是正常现象：插件先不弹窗、悄悄问一下已有的授权够不够，不够才正式申请，这时才弹窗（2026-10-10 实测：一次计算器任务里有两条这样的记录）。**不带** `silent` 的才说明插件没有配置成弹窗模式（`appApproval: dialog`），看「模式检查」 |
| 截图全黑，或者读不到 AX | 两项系统权限没给全：插件页「检查权限」，再按 2.5 授予；开关开着却不生效时见 6.1 |
